# QQ <-> Hermes bridge (NapCat/OneBot -> Hermes api_server)

Runtime pieces: bridge `$HERMES_HOME/scripts/qq-bridge.py`, config `$HERMES_HOME/qq_bridge.json`,
session map `$HERMES_HOME/qq_bridge_sessions.json`, log `$HERMES_HOME/logs/qq-bridge.log`.
It consumes QQ events, routes each sender to a Hermes profile (owner -> `default` full tools;
everyone else -> a guest profile whose `platform_toolsets.api_server` is reduced, e.g. `[web]`),
and pushes the reply back through the AstrBot OpenAPI. AstrBot/NapCat platform internals live in
the `astrbot-plugin-ops` skill; this one is the bridge itself.

## When to Use
- QQ messages get no reply, the wrong persona answers, group behaviour or per-sender permissions are wrong.
- Changing what the bridge feeds Hermes (images, quoted messages, forwarded chat records) or how turns are queued.
- A QQ message needs context to answer it — what the chat said around it, what a shared file/card was, whether anything is pending on the bot — pull that over the WS action channel (see Debugging) instead of guessing.

## Event feed
- **Subscribe to NapCat's OneBot WebSocket server (`ws://127.0.0.1:3001`), never rely on NapCat's HTTP report client.** The HTTP client can be `enable: true` in `onebot11_<uin>.json` and still post nothing at all — the WS server is the feed that actually delivers. Keep the HTTP `/qq` endpoint as a secondary path, deduped by `message_id`.
- Filter at the feed entry: only private messages and group messages that @-mention the bot spawn a worker thread; count and periodically summarise the ignored ones. Otherwise every line of chatter in a dozen groups spawns a thread just to be dropped.
- Group replies fire only on an @-mention: an `at` segment whose `qq` equals the bot uin, `[CQ:at,qq=<bot>]` in `raw_message`, or a configured wake prefix. The reply UMO is the group, the session key is `(profile, group, member)` — never one shared group session, or a guest rides the owner's full-tool session.
- **A wake *word* anywhere in the text is a first-class trigger, not just `@`.** The user's rule: in a group, saying the bot's name (default `大肥鱼`, config `group_wake_words`) counts exactly like an @-mention. Match the message *text* case-insensitively as a substring **in addition to** the `at` segment and the prefix list — a prefix-only check misses "帮我问下 大肥鱼 这事儿", and the user will report the bot as deaf. After the event feed connects, call NapCat `get_login_info` once and merge the bot's own current nickname into the wake list, so renaming the bot in QQ keeps the trigger alive with no code change.
- **Route `notice` and `request` events in *every* ingress, not just the WS feed.** Friend-added notices arrive on the same feed as messages, and the bridge has two entry points (the WS loop and the HTTP `/qq` endpoint). Adding the branch in one and testing through the other looks exactly like "the feature does not work": the POST still returns `{"status":"ok"}` and nothing is logged, because the pre-filter drops non-message events silently. Factor the handling into one function, call it from both ingresses, and log a line for every dropped event so a silent no-op is visible next time.
- **Decode inbound bodies strictly in BOTH ingresses, with a GBK fallback — the HTTP ingress is lossy today.** `/qq` does `raw.decode("utf-8", "replace")`, so an event body that is not UTF-8 (a GBK-encoded poster, a hand-rolled test harness) becomes `U+FFFD`-laden text and the destroyed bytes are gone for good; the WS feed hands you a `str` already decoded, so a `U+FFFD` there came from upstream (sender or NapCat), not from the bridge. Pattern: try `raw.decode('utf-8')`, on `UnicodeDecodeError` retry with `gbk`, and log which branch was taken. Recovering a message that already arrived mangled — and proving the reading byte-for-byte — is `references/inbound-text-encoding.md`.

## Concurrency
- **One turn at a time per chat.** Hold a per-chat lock for the whole turn. Two messages that arrive together for a chat with no session yet otherwise both `POST /api/sessions`; Hermes rejects the duplicate with `400`, and the loser posts "HTTP Error 400" into the user's chat.
- Retry session creation once with a different title, and re-read the session map under the same lock before creating — a lost race still happens around restarts. The duplicate-title rejection is `400` whose body names the offender (`invalid_title` / `... is already in use by session <sid>`): read that id out of the error and choose deliberately — reuse it (keeps history) or generate a suffixed title (intentionally fresh, e.g. after clearing a polluted session) — rather than blind-retrying.
- Cap queued turns per chat (drop + log when over the cap) so a burst cannot pile up forever.
- Write the session map atomically (temp file + `os.replace`) under a lock: several workers finish turns simultaneously and a plain rewrite corrupts the JSON.
- Serialize sends per chat so multi-chunk replies cannot interleave, and serialize the shared NapCat action socket.
- **The ack timer is a noise trap — leave it off.** A 「收到，我在处理」 broadcast sent from a `threading.Timer` (~25 s) was meant to keep a long turn from looking silent, but when the user fires several messages in a row every queued turn fires its own identical ack (each one also drags along that turn's meme decoration), minutes apart — he reports 「它一直在无限回复」 and the bot reads as stuck in a loop. Keep `ack_after_s` at 0 **in the running `qq_bridge.json`** — an absent key silently falls back to the code default where the timer lives, so the noise returns whenever the file is rewritten; verify the effective value by importing the module and printing `CONFIG['ack_after_s']`. If an ack is ever truly wanted, cap it to one per chat per several minutes, never one per queued turn.

## Long turns
- Set the per-request timeout above the longest plausible task (30 min here), not a transport default — a QQ task turn routinely runs for minutes.
- **The runtime `qq_bridge.json` overrides the code `DEFAULTS`, so read the JSON value before debugging a threshold.** A tuning value left in the code is inert once the file carries that key: the per-request timeout read `1800` in `DEFAULTS` while the live file said `300`, so every multi-minute turn (song search → download → ffmpeg) died as `Hermes 这边出错了：timed out` while the code looked correct. Same trap as `group_rate_limit_s` — change both places, and when a threshold misbehaves, grep the JSON first.
- **A helper the bridge spawns must be launched with an interpreter that has the bridge's own deps.** The send helpers import `websockets`; pointing a spawned service at a separate project venv made every send fail `连接失败：No module named 'websockets'` and return `None`, so the reply quietly fell back to text while the log still looked alive. Choose the child interpreter deliberately (config key), probe it once (`python -c "import websockets"`), and send the child's stdout to its own log file so a silent child is visible.
- **A client-side timeout does not stop the server-side turn.** Hermes keeps running and stores the final assistant message in the session; the user just never sees it. Recover by reading the session's last non-empty assistant message and posting it to the chat, with one line saying the earlier timeout notice was a false alarm.
- Detect "turn finished" from the session itself, not from a status field: `ended_at` stays `null` for api_server sessions, so treat a non-empty final assistant message that stopped changing for ~2 polls as done.

## Images, quoted and forwarded content
- `POST /api/sessions/<id>/chat` accepts a multimodal `message`: a list of `{"type":"text","text":...}` plus `{"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}` parts. The main model reads images natively — no separate vision provider needed. (`_normalize_chat_content`, the text-only flattener, is *not* the parser this endpoint uses; do not conclude from it that images are unsupported.)
- Resolve an image segment in this order: local `file` path (handle `file://`) -> `url` over http(s) with a browser-ish UA -> NapCat action `get_image` with the file id as the last resort. Then sniff the MIME from the file header, not the filename: QQ stickers are GIF bytes under a `.png` name and CDN URLs have no extension.
- Fetch that `url` through a **proxy-free opener**, not the ambient environment: QQ image URLs are Tencent CDN hosts that answer directly, while the default opener on a host running a local accelerator tries the accelerator first and dies `WinError 10061` as soon as the user turns it off (`[img] 下载失败` in the log). Keep one module-level `urllib.request.build_opener(urllib.request.ProxyHandler({}))` and use it for the image fetch — it does not depend on what the environment happens to hold.
- **A size cap sits in front of every fetch and exceeding it drops the image silently.** `_img_limit()` reads `max_image_bytes` (default `5_000_000`) from `qq_bridge.json`, and the reader/downloader stop at `limit + 1` bytes, so a multi-MB sticker (a phone GIF is routinely 5–7 MB) is discarded with only `[img] 拿不到图片内容，跳过` in the log and `N张图: 0` on the `[recv]` line — the turn still runs, so the model answers "你没发图" while the URL itself downloads fine by hand. Read the `[recv]` line's image count as the ground truth for "did the model see it", raise the runtime JSON key (the file wins over `DEFAULTS`) and restart the bridge; do **not** go fixing the fetch path.
- **An image the bridge dropped is still recoverable by hand — replay the path it would have taken.** `get_group_msg_history {group_id, count: 15}` returns recent messages *including* their `reply` segments; a `reply` segment only carries an id, and that id is the **quoted** message, so `get_msg {message_id: <reply data.id>}` yields the real `image` segment with its CDN `url` — which is where the picture actually lives when the sender answers by replying with a sticker. Download it through the proxy-free opener, and for an animated sticker open it with PIL and paste frames `0, n/2, n-1, …` into one montage PNG before looking: a speechless 75-frame GIF shows nothing legible in a single frame. Vision sees the montage natively, so this costs one look and lets you answer the user in the same turn instead of asking them to resend.
- An image-only message must still produce a turn — fall back to a text part such as "（对方发来图片，没有文字，请看图回应）".
- Parse `reply` (quoted message) and `forward`/`node` (chat-record card) segments, fetching `get_forward_msg` and flattening its text+images. Unparsed segments make the model answer "you sent nothing", which reads as the bot being broken.

## NapCat action channel
- Keep ONE long-lived WS to NapCat and match responses by an `echo` id through a waiter map, instead of a fresh WS per action (each image fetch otherwise pays a handshake).
- Liveness check: `ws.protocol.state` is an IntEnum, so `str(state)` is `"1"`, not `"OPEN"`. Compare `getattr(state, "name", ...)`. A substring check on the string silently reconnects on every call.

## Keeping it running (must outlive the gateway)
- **Never start the bridge from the agent's own terminal and call it persistent.** A helper launched there is a child of the gateway process tree, so `hermes gateway restart` takes it down with it and QQ silently stops answering — start it detached through a hidden `wscript.exe` launcher (recipe, recovery layers and verification in `references/bridge-operations.md`).
- Give the bridge a single-instance guard (probe the listen port, log, exit) so the login item, the watchdog and a manual start cannot stack two bridges on one port. The guard still races (two starts in the same second both see a free port): make the loser exit on the bind error instead of running on, and when diagnosing, check *which* PID owns the port (`netstat -ano | grep ':8790 .*LISTENING'`) against the PID whose stdout the launcher redirected — an orphaned second instance eats the same events, so the log and the live behaviour disagree (the log stops growing while `/health` keeps advancing `last_event_at`, and the process count is higher than the number of launchers you started).
- Keep two recovery layers: a Startup-folder login item for reboots, and a repeating scheduled task that starts the bridge whenever the port is not listening. Verify by killing the bridge and watching the watchdog bring it back — do not assume the mechanism fired.
- **Strip the host proxy out of the bridge's own loopback calls.** On a machine running a local accelerator (Clash/V2Ray-style, `127.0.0.1:7890`) a bridge started the usual way inherits `HTTP_PROXY`/`HTTPS_PROXY` without `NO_PROXY`, and then routes *loopback* through the proxy too: `urllib.request.proxy_bypass('127.0.0.1:3001')` returns `False`, so `websockets`' default `proxy=True` connect goes to the accelerator and dies `WinError 10061` the moment the user quits it. Fix it inside the process at startup — force `127.0.0.1,localhost,::1` into `NO_PROXY` **and** `no_proxy` (covers the urllib calls to the api_server and the bot framework), connect with `proxy=None` (retry the plain call on `TypeError` for older `websockets`) — because a launcher or scheduled task inherits whatever the host has today. Belt and braces for the bridge's own HTTP calls (api_server, bot framework, image fetch): keep one module-level `build_opener(ProxyHandler({}))` and use it everywhere local/domestic, so the fix does not depend on the environment at all. Reproduction and the exact snippets: `references/bridge-operations.md`.
- Monitor the **feed link**, not just your own port. The bridge can be alive, listening and reconnecting every 5 s while NapCat's OneBot WS (`3001`) is down — the user then reports "QQ 收不到消息" while every probe of the bridge looks healthy. The feed cannot be relaunched by a script (it lives inside the QQ client), so the watchdog should alert on that port instead of trying to fix it; the cure is a QQ-client restart (unless the hook has gone stale against an updated QQ — third case below). Three causes produce this same log, so discriminate before acting with `curl -s -o /dev/null -w '%{http_code}' --noproxy '*' http://127.0.0.1:3001/`: `426` (an HTTP request to a WS endpoint) means the feed is healthy and the failure is the proxy case above; no answer means the port is not served at all — then separate **client down vs account not logged in**: NapCat's WebUI port (`6099`) answering while `3001` is dead, plus a freshly written `NapCat.Shell/cache/qrcode.png`, means the bot account is sitting at a login QR waiting for the owner to scan. The OneBot listener is configured *per account* (`onebot11_<uin>.json`) and only loads once that account is online, so a logged-out account produces exactly "6099 up, 3001 gone" — that is not a config regression, and do not go hunting in the config for it. **Both ports dead with QQ itself exiting seconds after launch is the third case: the NapCat hook no longer matches the installed QQ.** QQ updates itself in the background and the hook is packed per QQ build, so after an update QQ starts under `--enable-logging`, the boot main resumes it, and it dies — `NapCatWinBootMain.exe` prints its argv block and `Process exited.` within seconds, the QQ process count returns to 0 in under ~10 s, and neither port ever listens. Read the two versions instead of guessing: the build the hook was packed for is `version` in `NapCat.Shell/qqnt.json`; the installed one is `(Get-Item 'C:\Program Files\Tencent\QQNT\QQ.exe').VersionInfo.FileVersion` (and a staged `<old>-<new>.zip` under `QQNT/versions/` means another update is pending and will break it again). On a mismatch the QQ-client restart above does nothing — update `NapCat.Shell` to the release whose notes name the installed QQ build. Back up `NapCat.Shell/config/` first (it holds the login session, e.g. `napcat_<uin>.json` / `onebot11_<uin>.json` / `webui.json`), overlay the new release's files, keep `config/`, then re-inject. Four things that cost a full round of false leads:
- **Verify the downloaded release before extracting.** `curl -C -` on a flaky link leaves a file that `tar -tf` lists fine but that fails mid-extract (`ZIP decompression failed` on `native/napi2native/napi2native.darwin.x64.node` — a macOS binary, so it looks unrelated to Windows). Compare `sha256sum` with the asset's `digest` field from the GitHub API and re-download whole if it differs; do not trust a resumed download.
- **Re-inject through the launcher's environment, not by calling `NapCatWinBootMain.exe` directly.** The boot main reads `NAPCAT_PATCH_PACKAGE` / `NAPCAT_LOAD_PATH` / `NAPCAT_INJECT_PATH` / `NAPCAT_MAIN_PATH`, which the launcher sets before it execs — invoked bare, QQ is resumed and then dies within seconds exactly like the version-mismatch symptom, so you "confirm" a theory you have already fixed. Set all four (or call the launcher) and the same binary boots a healthy QQ.
- **Admin is not required — but the shipped `launcher.bat` insists on it.** It checks `net session` and re-launches itself elevated through `launcher-elevate.ps1 ... wt.exe`, which an agent session cannot approve (no UAC prompt ever renders). `launcher-user.bat` is the same injection without the check and works unelevated. Put the four env vars + the launcher call in your own no-`pause` `.cmd` (the shipped scripts end in `pause`, which hangs forever in a background/non-interactive run) and drive that from the VBS/Startup item; do not point the login item at `launcher.bat` or every boot waits on a UAC dialog nobody answers.
- **NapCat ships its own GitHub mirrors** in `napcat.mjs` (`gh.5050net.cn`, `gh.inkchills.cn`, …) for when github.com is unreachable. They are rate-limited hard (429) in practice, so prefer asking the owner to switch the local accelerator back on — with it on the same download went 5 MB/s vs ~30 kB/s direct. When you do read that file, read it properly: listeners nest under `network.websocketServers` / `network.httpClients`; a top-level `websocketServer` lookup returns empty and sends you chasing a non-problem. Have the bridge report its own feed state in `/health` (`ws_connected`, `last_event_at`) and alarm on `ws_connected == false` — the port probe passes in the proxy case.
- The launcher must discover the interpreter (probe candidates under `installs/*/environments/*/venv` for the dependency marker) and the bridge must fall back to reading `API_SERVER_KEY` from `$HERMES_HOME/.env`: a VBS/task launch inherits no environment, and install paths change on update.
- Prove detachment from the process parents (`parent is gateway = False`), not from the fact that it started.

## Debugging
- Read the log with `grep -a` on the exact field (`[in]`, `[recv]`, `[send]`, `[error]`) rather than `tail -n`. A long turn pushes older lines past the tail window and "the event never arrived" is then a false conclusion.
- Log the inbound segment kinds (`segs=['at','image','text']`) plus sender/group on every message. A silent non-reply is almost always an unparsed segment kind, not a routing failure.
- **Read the reply text, not just the send status.** When every reply the bot posts is an English provider-auth error, routing and delivery both worked — the sender's *profile* is the problem: a profile `.env` shadows the main one, so one stale key breaks that profile while the owner keeps working. Diagnose from the key tail in the provider's 401 and repair per the provider-credentials section of `references/bridge-operations.md`.
- **Test the routing predicate in-process before touching the live bridge.** Load the module by path (`importlib.util.spec_from_file_location`) — module level only reads config, since the server starts in `main()` — and assert `should_handle()` on synthetic events: name inside a sentence, plain chatter, an `at` segment, a private message, and (once) a near-miss like "肥鱼". Six table-driven cases catch a wrong matcher in a second, with no restart and nothing sent to a real chat. The same probe extends to whole branches: monkeypatch `_steam_now` / `ask_hermes` / the dispatch helper (`_start_singing`, the image job) with recording stubs and call `handle_event()` on a synthetic event with a **fake group id** — the game gate for song/draw orders is then provable end-to-end without a real LLM call or a live chat (the only noise is the send failing on the fake group, which the log also proves was the *only* action taken).
- **「它不回我」先查三件静默丢消息的事，再怀疑链路**：(1) `grep '\[skip\] rate limited'` —— 桥接有每成员每群的冷却窗，用户连发两句时第二条被**静默丢掉**，观感就是「不回」；把窗口压到约 1 s（`group_rate_limit_s`，运行时配置与代码默认值一起改）并保证丢弃时打日志。(2) 只有 `@` 没有文字（或只 @ 了一个表情）的消息**必须回一句**——曾经「按设计跳过」，结果就是「@ 了它它不理」被当成故障报上来（用户问「这个群你不发消息了」）。做法：内容为空但机器人被叫到时，塞一句占位文本（如「（对方只 @ 了你，没说话）」）走正常回合；只有既没被叫到又没内容的才丢。(3) 只在群里没叫到名字时才走 `已忽略 N 条无关消息` 计数——用户以为叫了名字却没被接住，就去核对他那条到底带没带唤醒词。三件都排除后才是链路层（`ws_connected`、3001、代理）。
- **重启桥接、或任何按模式杀的自家进程（`game-mode.py`、看护脚本……）时按进程名过滤，不要按命令行关键字**：`CommandLine -like '*qq-bridge.py*'`（把模式换成 `'*game-mode*'` 同样中招）会连你自己那条正在执行的 shell 一起杀掉（它的命令行里同样含这个字符串），命令当场断在半路，后续步骤全没跑。用 `-Filter "Name='python.exe'"` 再叠 CommandLine 匹配，或者直接按监听端口的 PID 杀。
- **An allow-rule usually exists twice; patching one copy is the same as patching none.** The ingress pre-filter (`should_handle()`) and the handler body each decide "is this message for the bot?" — a group bypass added only to the pre-filter still gets dropped by the handler's own `@`-or-wake-word check, silently, before it logs `[recv]`; the user then reports "QQ 不说话了" while every probe of the port, the feed and the profile looks healthy. Before trusting any bypass, `grep` for the other copies of the same predicate (`mentioned_bot(`, `should_handle(`, `owner_qq`) and make both call one shared predicate. Prove it by injecting a synthetic event — see the probe bullet below — not by reasoning.
- **Run in-process probes with the interpreter the bridge actually uses, not the default Hermes runtime one.** The launcher picks whichever `installs/*/environments/*/venv` carries the dependency marker, and that is often *not* the venv the gateway uses — probing with the wrong python dies in about a second (`No module named 'websockets'`, a send action returning `None`) and looks exactly like a broken bridge. Read the real interpreter off the process command line (`Get-CimInstance Win32_Process` for `qq-bridge.py`) or the launcher's discovery logic (`for p in installs/*/environments/*/venv/Scripts/python.exe; do "$p" -c "import websockets"; done` — the first that prints nothing is the right one; the venv the gateway itself runs on usually lacks it), then load the module by path (`importlib.util.spec_from_file_location` — safe, the server starts in `main()`) and call the helpers directly. This is also how to pre-warm audio: `_make_voice(text)` then `send_voice(umo, path)`, with the cached mp3's path printed for the user to play.
- Verify a fix with a real probe: post a synthetic event (`POST /qq`) using fake ids so nothing reaches a real chat, then grep the log for the `[in]`/`[recv]`/`[send]` triple.
- **A group you receive events from but can never send to is a synthetic event, not a delivery bug.** NapCat answers `retcode 1200` (`EventChecker Failed`) and the bot framework `HTTP Error 400` for `GroupMessage:<gid>` while the same send path works for real groups — that combination means the event was fabricated (a harness posting into `/qq`, a test id such as `999999901`) for a group the bot is not in. Check whether the id is even in the bot's group list (NapCat action `get_group_list`) before touching the send path; do not "fix" sends for a group that does not exist, and tell the user replies to it cannot land.
- **A garbled message is an encoding fault, not a user typo or a model failure.** Read the raw bytes of that log line with Python (`open(...,'rb')`, slice by an anchor such as the group id) instead of a text view: `U+FFFD` shows there as literal `EF BF BD`, which is how you tell "the bridge received bad bytes" from "the log itself is mangled". Then recover and verify per `references/inbound-text-encoding.md` and say which characters you inferred — lost bytes make a reading plausible, never certain.
- Identify who listens on which port from the PID: `netstat -ano | grep LISTENING | grep -E ':(3001|6185|8790|9880|8642|7899) '`, then `tasklist | grep <pid>`; `tasklist //FI "PID eq <pid>"` prints nothing under git-bash, and `powershell -NoProfile -Command "Get-Process -Id <pid> | Select Id,ProcessName,Path"` gives the exe path (`QQ.exe` on `127.0.0.1:3001` is NapCat living inside the QQ client, not a separate process to restart).
- **Group facts (member counts, who is an admin, recent messages, every group the bot is in) are one WS call away — don't reconstruct them from the bridge log, which keeps only *triggered* messages (everything else is counted, not stored). A triggered message's meaning usually sits in the untriggered chatter around it; pull the neighbourhood before answering, and fetch any shared artifact too — file segments carry their own download URL, so read the file before commenting on it.** The event socket is a full OneBot action channel: run a scratch script with the *bridge's* interpreter and connect `websockets.sync.client.connect("ws://127.0.0.1:3001", proxy=None)` (proxy trap above; the socket also pushes live events to every client, so skip any frame whose `echo` is not yours). Useful actions: `get_group_list` (each group with `member_count`/`max_member_count`), `get_group_info {group_id}`, `get_group_msg_history {group_id, count}` (includes `reply` segments, but they carry only an id — not the quoted text), `get_group_member_info {group_id, user_id, no_cache: true}` (`role` = owner/admin/member; `retcode 1200 EventChecker Failed` = that user is not in that group). Ready-made: `scripts/napcat_query.py` (`groups` / `history <gid> [n]` / `member <gid> <uin>`) — extend it rather than hand-rolling a scratch probe. The same channel answers the private side and "is anything pending": `get_friend_msg_history {user_id, count}` (a private chat's tail), `get_group_system_msg` (pending invites / join requests), `get_doubt_friends_add_request` (friend requests, possibly stale) — empty lists mean nothing is waiting on the bot. A logged `[request]` line is informational only — the bridge never auto-accepts anything, so check those calls instead of reading the line as unhandled work.

## Dispatching heavy side tasks from chat (song orders, model runs)
- **Parse the request name with *and* without quotes.** A parser that only accepts `《...》` silently degrades 「唱一首平凡之路」 to "something random" and the bot sings the wrong song — the user notices immediately. Match the trigger, then take the remainder of the string as the name, and keep the same rule in both the bridge (dispatch decision) and the service (execution) so they cannot disagree; table-test both on the same inputs.
- **A trigger that only covers `唱…` drops the order in silence.** Users type 「点一首 X」, 「点歌手名」, 「唱《X》」, 「唱一首 X」 — a parser that recognises one and not the others returns "nothing to do" with no message and no error, and the chat simply goes quiet, which reads as the bot ignoring the order. Cover every phrasing a user has actually typed in *both* layers, log every unrecognised trigger line, and when dispatching by hand rewrite the text into a form the parser accepts (「点一首 X」→「唱一首 X」) instead of passing the raw sentence.
- **A singer name is not a song.** Library lookup by name is an unordered substring glob, so 「点一首南征北战」 happily returns any track by that artist (which one is luck of the glob order). Resolve to one concrete title before dispatching — pick the artist's best-known track, or ask in a single short line — never let the glob choose.
- **Gate a GPU/CPU-heavy side task on the owner's state before dispatching.** Read what he is playing from the bot framework's own watcher cache (`astrbot_plugin_steam_monitor`: `plugin_data/.../last_states.json` → `gameextrainfo`, matched by steam id), falling back to the Steam Web API (`ISteamUser/GetPlayerSummaries` with the key/steamid from that plugin's config), and cache the answer ~60 s. If he is mid-game, do **not** start the job: return an instruction telling the model to answer with ① the concrete game (from the probe, never invented) ② why it must wait (the job competes for the same card and would stutter his game) ③ come back in ~half an hour — one or two witty spoken sentences, composed by the model, not a template or a list.
- **Resolve the name to a concrete audio source inside the spawned service, never in the chat turn.** A chat turn that runs browser → download → convert blows the request timeout and goes silent mid-reply; the service subprocess has no such limit and logs its own progress.
- **Anonymous B站 search that actually works (no cookies, no browser).** `yt-dlp bilisearch` answers 412 and `--cookies-from-browser` is stopped by Chrome's app-bound encryption, but the plain endpoint is fine once the visitor id is present: `GET https://api.bilibili.com/x/frontend/finger/spi` → take `data.b_3`/`b_4`, then `GET https://api.bilibili.com/x/web-interface/search/type?search_type=video&keyword=<urlencoded>` with `Cookie: buvid3=<b_3>; buvid4=<b_4>`, `Referer: https://www.bilibili.com/` and a browser UA → `code:0` and ~20 hits carrying `bvid` + `duration`. Without the buvid the same URL returns an HTML page, which reads like "the search API is blocked".
- **Score the hits; never take the first one.** The top result is regularly a 「XX是什么梗」/解说 clip that would be sung verbatim. Add for 原唱/官方/MV/完整版/无损/音频/歌曲 in the title, subtract for 梗/指南/解说/伴奏/纯音乐/教程/合集/鬼畜, add for a 2:30–6:40 duration (longer is usually a compilation) and for the queried name appearing in the title, then accept only above a floor score; try keyword variants 「<name> 原唱」「<name> 歌曲」「<name> 音频」 in turn.
- **Who may order is policy the user changes — re-read it before enforcing the old one.** Orders were owner-only, then opened to **everyone** (group and private), and separately outsiders' requests for library-missing songs were allowed to auto-download **inside the singing service only** (they never get a tool or a shell). The one gate that stays constant is the owner's state: while he is in a game nothing is sung, no matter who asked. Keep the policy in config, and when it changes, fix the sentence in the skill instead of re-deriving the old rule.
- **Confirm the artifact landed by reading the chat back, with the window sized to the elapsed time.** A file-upload call returning success is not delivery: pull `get_group_msg_history {group_id, count}` and look for your own `file`/`record` segment plus its timestamp. `count` counts messages, not minutes — in a live group a fixed `count: 10` covers only the last few dozen seconds, so a check run minutes after the send sees chatter only and the delivery falsely looks failed. Size it to the elapsed span (≈30–50 for a few minutes) and match on timestamp, not on "it is somewhere in the tail".
- Run the job **detached with its own log file** and let it post its own «started / here it is» lines, so a multi-minute turn never holds the bridge's request timeout open.
- **Image orders are the same shape** (`image_service.py` next to the ComfyUI install, spawned by the bridge): the bridge only decides *whether* it is an image order and *what* the prompt is, then spawns a process that boots ComfyUI on port **8189**, generates and posts the picture back through a NapCat `image` segment (`_file_uri` again — a bare Windows path is read as a URL and fails "识别URL失败", same as `record`). NEVER reuse 8188: that is the owner's MiniMax-H3 video server, and its scripts treat "8188 answers" as "my video server is up".
- **A self-referential draw order must have the self-reference expanded before dispatch.** 「画一张本鱼」「画一个自己的样子」 extract to prompts like「本鱼」/「自己的样子」— the model has no idea who that is and renders a random stranger (measured live: the group asked 「这是什么」 about the result). `_expand_self_prompt()` in the bridge: a pure self-reference (本鱼/大肥鱼/你自己/自己…的样子) is replaced wholesale by the look description (`_SELF_DESC`), and 本鱼/大肥鱼 inside a longer prompt are substituted in place (「画一张本鱼在吃白米饭」→ description +「在吃白米饭」). Keep all three phrasings as table-test cases whenever the extraction logic changes.
- **Alternation is ordered, not longest-match — write 「图片」 before 「图」.** `(?:图|图片|照片)` matched the short branch and left `片：一只可爱的柯基` as the prompt. Same family: `画个` consumed the noun in 「给我画个头像」 and the extraction returned empty — keep a fallback that re-reads the text after the match when stripping leaves nothing, and take the image noun itself as the prompt. When no subject is extractable at all (「画张图」, or only the trigger arrives), do not render: fall through to the model with a one-line nudge to ask what to draw — an order must say what to draw before a 30 s render is queued.
- **Two trigger tiers are what keep 「来一个笑话」 safe.** Strong: `画|绘制|生成` + measure word, or any verb + an image noun. Weak: `来|跑|整|搞|做|捏` + measure word, accepted **only when the message also carries an image noun** (图/图片/头像/壁纸/表情包) — without that, 「来一份外卖」 and 「来一个笑话」 start rendering. Add a small non-visual blocklist (想法/方案/总结/代码/故事…) so 「生成一个想法」 does not queue a 30 s render, and a negative lookbehind `(?<![在正别没])` so the narrative 「我在画图」/「别画图了」 doesn't fire. Table-test both layers on the same inputs; keep every case that ever misfired in the table.
- **A local model has no content moderation — the bridge has to be it.** What gets banned is the *account*, when hardcore output lands in a group. Gate on an explicit-term blocklist in the **bridge** (let the model compose the refusal line, 大肥鱼-flavoured) *and* in the spawned service as defence in depth — the service layer is what actually caught the first live violation, in the window before the bridge had its gate. Keep the list to unambiguous adult terms (做爱/裸体/色情/淫/幼女/nsfw/naked…) so ordinary fan-service requests still render.
- **Per-request processes must not each linger.** A job that stayed to watch its own 5-minute idle wait piled up **10** python processes under a burst; worse, a job that returned early (blocked, errored, no ComfyUI) left *no* watcher at all and the 4.5 GB stayed resident forever. Send the image, exit, and delegate idle-shutdown to one detached watcher (`image_service.py --watch <idle_s>`, singleton enforced by a heartbeat file, kills the 8189 listener once `last_use` is stale and no job lock is held). Verify it by running the watcher with a short idle and watching the port drop.
- **Let blocked requests rejoin the normal chat turn instead of answering directly.** When the gate or the game check fires, rewrite `content` with an instruction for the model ("…response in one or two spoken sentences, no lists, don't mention filters") and fall through — a hard-coded refusal string reads like a robot and cannot adapt to who asked.
- **ComfyUI pops a browser window on every start unless you say otherwise.** `comfy/cli_args.py` does `if args.windows_standalone_build: args.auto_launch = True`, and the standalone launcher always passes that flag — with an on-demand lifecycle (start per job, close when idle) that means one new browser window *per drawing*, which reads as "the bot keeps opening browsers". Confirm the correlation before believing it: compare the browser processes' `CreationDate` against the ComfyUI ready timestamps in the service log; they match to the second. Fix at the launcher (`--disable-auto-launch`; the disable check runs after the standalone one, so it wins) — the manual desktop path is unaffected because its .bat opens the browser itself. Re-check after any ComfyUI upgrade.
- **Relaxing a group rule means relaxing it in *both* gates.** `should_handle` (the cheap pre-filter) and `handle_event` (the real dispatch) each re-check "@ or wake word", and the inner one returns **silently**. Editing only the outer one gives: the `[in]` line appears in the log and then literally nothing else happens — no `[recv]`, no error. Put the decision in one shared helper and call it from both. Do not build per-feature bypasses of the mention requirement: the narrow "only image orders" window in this file was removed again at the owner's request after it caused uninvited renders — in groups every trigger (chat included) is @-or-name.
- **A broad verb+noun rule will match statements about the speaker's own actions.** 「我昨天画了张图」 contains verb→measure→noun and would queue a render; reject when 了/过/完 follows the verb. Every relaxation of the matcher needs a table-test line for the plain-chatter sentence it could newly swallow.
- **Detect on the user's words only — never on the text the bridge synthesised.** An image-only message gets a placeholder (「（对方发来图片，没有文字，请看图回应）」) and a reply gets `[被引用的消息] …` appended; both then flow into `text`, and a detector run on that matches its own scaffolding — a user who sent a bare photo got a generated picture back. Split the synthesised tail off before detection (drop everything from `\n[被引用的消息]`, drop the placeholder), and keep the detection input identical in the bridge and the service.
- **Match with three tiers, widest last, and reject meta-talk.** A verb+measure-word rule misses 「帮我生成色图」「帮我生成这个人穿泳装的照片」 because the noun sits behind other words — add a broad tier (画|绘制|生成 with an image noun inside ~12 characters) and a weak tier (来|跑|整|搞|做|捏 + measure word). What makes it safe is the *rejection* lists: a non-visual noun after the measure word (「生成一个想法」) and — the one that bit the owner himself — meta-talk after the image noun, because 「画图权限没有开放给每一个人」 matched verb+noun and got a nonsense render queued in a live group. Keep real misfires from the logs as table-test cases in both files.
- **Image orders from a *replied* image are a different feature: img2img.** A reply segment carries only a `message_id`, so resolve it with `get_msg`, pull the image out as a data URL and run the denoise workflow (`LoadImage` + `VAEEncode`, denoise ≈0.75 keeps composition and changes the subject) instead of `EmptySD3LatentImage`. Cache the `get_msg` result — the same turn needs the replied image twice (once for the model's content, once for the dispatch) and without a cache you fetch and download it twice. Strip the pointing words out of the prompt («把这张改成戴墨镜的猫» → «戴墨镜的猫»): the model renders the *result phrase*, not the instruction.
- **Meta-talk sits on both sides of the trigger, so guard both.** Checking only what *follows* the match left 「…才能**触发这个画图**，还有以后我打游戏的时候…」 matching verb+noun, and the rest of the owner's sentence was used as the render prompt. Add a pre-check for the words just before the match (触发/这个/那个/才能/关于/提到…) as well as after it, and keep the owner's own complaints as test cases — the messages about the feature are the ones most likely to trigger it.
- **Game mode: react to the existing game probe instead of building a new one.** The Steam check that the game/voice gates already use (`_steam_now()` → the bot framework's watcher cache, Steam Web API fallback) is the same signal — a small daemon polling it every 30 s can stop the GPU/RAM-heavy self-started services and restore them afterwards. Rules that keep it safe: only touch services **we** started (never the user's browser, game, or system processes), remember which ones were actually running and restore exactly those, persist the state to a file so a daemon restart doesn't strand the machine in game mode, and debounce the exit (≈3 polls) because the Steam status blips to "not playing" during map loads and server switches. Keep the transitions **silent for the owner** — he asked not to be messaged on game start/end (『自己知道就好』), so leave `NOTIFY=False` in `game-mode.py`: services close and restore without a chat notice, and only an explicit future request should re-enable it. Keep the list of what to close in config/constants, not in the detection code.
- **A local model has no content moderation, so the blocklist has to grow from what actually arrives.** The first list missed 色图/涩图/裸着/不穿衣服 — all of which real users typed within an hour — so re-read the group log after launch and add the terms people actually use, not the ones you'd write.
- **Check the persona before concluding the feature is broken.** Users reported "it won't draw for me" when the pipeline was fine: the phrasings simply weren't parsed, *and* when the request fell through to the model the chat instructions produced 「本鱼是只会打字不会画画的鱼」. Whenever a capability is added, state it in every instruction set that can answer about it (owner / second owner / guest) and forbid the "I can't do that" phrasing — otherwise the assistant denies having the feature you just built.

## Shared-file discipline (more than one session edits this script)
- The write is last-writer-wins and a full-file rewrite silently drops the other session's fresh fix. Re-read the file before patching, change only the lines you mean to change, and grep for your own markers after any other writer or a restart.
- Restarting the bridge aborts in-flight turns (their replies are lost): sample a busy chat's message count twice ~10 s apart before restarting. The server-side turn survives, so the answer is still recoverable from the session.
- Make the contract explicit instead of trusting goodwill: put the script directory under git, take an advisory per-file lease before editing (`agentlock.py acquire <path> --owner <name> --reason "..." --ttl 900`, plus `release` / `status` / `prune`; a conflicting acquire exits 1 and prints holder + reason + expiry), commit every change with a message, and append one line (`time | who | file | what | impact`) to a rolling `PROGRESS.md`.
- **Never coordinate through a chat-bound session.** POSTing a note into a session that a bridge or gateway serves can surface in the real chat; put requests in an `INBOX.md`-style file and answers in `PROGRESS.md`, and state the rule in shared memory so every session of the profile loads it regardless of cwd. To check whether something already leaked, pull `get_group_msg_history {group_id, count}` for the chat and grep the text.
- **Wake/policy flags are shared mutable state between sessions — put the owner's standing rule where both sessions read it.** A no-@ window added by the other session at the owner's request became *this* session's bug report the next day, and telling who set what took a git-log dig. Whenever the owner states a trigger/wake policy, change the flag and write the rule into the tracked `INBOX.md` in the same turn; before debugging "why does it answer uninvited", re-read the live `qq_bridge.json` (and the sibling session's recent commits) instead of trusting what you set earlier.

## Persona / voice
- The outward persona is not in the bridge: it lives in `$HERMES_HOME/SOUL.md` (default profile) **and** in the same file for every guest profile the bot speaks through (`profiles/<guest>/SOUL.md`) — a persona written only to the default profile never reaches guests.
- `SOUL.md` is read when a session's system prompt is built, and a **live** session keeps that prompt cached inside its running agent (`state.db.sessions.system_prompt` is NULL on this install, so the cache is in memory, not in the row). Editing `SOUL.md` therefore reaches only sessions created afterwards — verify the file itself with a throwaway api_server session per profile.
- To move *existing* sessions onto the new persona, pick one of two paths (recipes in `references/bridge-operations.md`, tool `scripts/soul-refresh.py`): **inject** the persona text into the old session as a message (immediate — but a restricted guest profile often refuses it as a chat-channel message pretending to be system, which is correct behaviour, not a bug), or **restart the gateway** so every session rebuilds from `SOUL.md` on its next turn (definitive).
- Report which sessions still carry the old voice instead of claiming the persona is live everywhere; a live in-memory prompt does not follow the file.
- **Give each channel its own voice with the api_server `instructions` field, not by editing `SOUL.md`.**`POST /api/sessions/<id>/chat` accepts an optional `instructions` string: the server applies it as session-level guidance, remembers it for later turns on that session, and it does **not** show up in the visible chat history the way prefixing every message does. Use it for per-channel behaviour. The user's standing split is **WeChat = task channel, QQ = chat only**, so the bridge sends instructions telling the model to sound like a real person: one or two short sentences, spoken register, no headings or numbered lists, never "我在处理/已完成/任务进度" status reporting, knowledge questions answered in three or four witty sentences instead of a lecture, and requests to do work answered with「这种事去微信找主人」followed by a return to small talk. Keep that text in the bridge config so the user can tune it without a code change.
- **Capability tiers are per *sender*, not per chat, and instruction text is remembered per session.** Selecting by profile alone breaks the moment the user wants a second privileged person: route on the sender id (owner → may dispatch work; a secondary "master" → addressed warmly but restricted to chat/search; everyone else → chat only) and keep every tier's text in config. Changing that text does **not** rewrite sessions that already exist — the earlier guidance is replayed from the session — so delete the affected entries from `qq_bridge_sessions.json` and restart before believing the new rule; otherwise the privileged user keeps getting told to go elsewhere and reports "它没按指令做事".
- **Identity questions have one standing answer: 「是本鱼主人（QQ 1568468）弄的」.** Asked 「你是谁做的 / 你的本事谁弄的」, the bot says its master (QQ 1568468) made it — phrased fresh each time, never boilerplate. Write it in **two** places: `SOUL.md` (reaches new sessions) and every instruction tier in the bridge (chat / owner / second owner), because live sessions replay what they already remember. Before editing the tiers, check whether `qq_bridge.json` carries its own copy of a `qq_*_instructions` key (a JSON copy silently wins over the code default); after restart, verify all three senders' effective text with `instructions_for(uin, profile)`.
- **Reply in short paragraphs, sent as separate messages.** The user's standing complaint is that one long wall of text reads as AI ("要分段说，一长段一看就是AI"). Split on paragraph boundaries, keep each chunk to a sentence or two, send in order with a small gap, and serialize the sends so chunks from two chats cannot interleave.
- **New friends: send one shortest-possible greeting, and never accept the request yourself.** The owner approves friend requests by hand; the bridge only reacts to `notice` / `notice_type: friend_add` by sending one private message such as 「你好呀」 (config `friend_greet_text`). No self-introduction, no capability list, no 「有什么可以帮您」 — that opening line is the clearest tell of a bot and the user will call it out. Log incoming `request` events (who, comment, flag) so the owner can approve them, but never auto-accept, and repeat the same rule inside the chat instructions so the first *message* from a new friend is equally short. Send that greeting as **voice**, not text (`friend_greet_voice`, default on): the user's ask is 「你可以发语音了，而不是发你好文字」— a typed 「你好呀」 from a stranger still reads as a bot, a one-line voice message reads as a person. Reuse `_make_voice` + `send_voice` with the text path as the fallback, skip the voice while the GPU is busy with a game, and pre-warm the greeting once at startup (call `_make_voice(greet)` before it is needed) so the first new friend does not pay the TTS cold start.

- **Group wake stays @-or-name for EVERYONE, the owner included; the owner's privilege is power, not wake.** An owner-wide no-@ bypass (`group_owner_always`) makes the bot answer every casual line he types in a group: it butts into human-to-human conversations with analyses nobody asked for, and he reports it as 「没人触发它，它突然冒了一句」. Default that flag **off**, require the wake word / @ in groups for all senders, and keep private chats ungated (that is where 「想随便说就私聊它」 lives). If the user later asks for no-@ commands again, treat it as an opt-in per-chat flag, not a global default — and expect to remove it again. The per-feature no-@ window for image orders (`image_group_no_mention`) was granted and then revoked the same way, with the added rule that an order must say *what* to draw (「画一张什么」) before anything renders. In groups, everything — chat, song orders, draw orders — goes through @-or-name; the feature gates only decide what an accepted message means. When one trigger type still fires uninvited, sweep **all** the flags together (`grep -n 'no_mention\|owner_always' qq_bridge.json`) rather than fixing the one you remember.

## Voice replies (answering with the cloned voice instead of text)
- **Send voice as the OneBot `record` segment**, not by uploading anything: `send_group_msg` / `send_private_msg` with `[{"type":"record","data":{"file":"file:///C:/path/line.mp3"}}]`. NapCat transcodes mp3 → QQ's silk itself, so there is no manual conversion step.
- **A bare Windows path is parsed as a URL and the send fails** (`文件处理失败: 识别URL失败`) even though the file exists — pass the `file:///` form; reuse whatever `_file_uri()` helper the image path already uses. The action channel is the same reusable NapCat WS, so no new plumbing is needed.
- Keep the chat readable: synthesise as voice only replies under a configurable character cap (≈90 chars) and let longer answers go out as text; on synthesis *or* send failure fall back to the text path so a reply is never lost; cache the audio by a hash of `(reference, text)` so a repeated line is not re-synthesised and the TTS server's cold start is paid once. Log the synthesis+send time per line — a silent 60 s wait reads as the bot being broken.
- **The cloned-voice server shares the card with the user's games, so slow voice is a latency report — not a reason to turn the voice off.** With a game running the same line went from 2–8 s to ~36 s and the answering turn stretched past 4 minutes, so the user reports 「QQ 不回消息了 / 你不回我」 while every `[recv]`/`[send]` line in the log is healthy: answer that from the timestamps and the per-line synthesis timing, never as a routing bug, and do not go hunting in the bridge.
- **Never silently downgrade the voice to text when the GPU is busy.** Probing `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv,noheader,nounits` (≥60 % util or ≥3 GB used → "gaming") and sending text instead produced 「现在语音怎么消失了？」 within the hour and had to be reverted: the clone voice is the feature the user asked for, and a fast reply that quietly drops it is worse than a slow one that keeps it. A slow-but-present voice is the default; if a downgrade is ever wanted it is an **opt-in flag that defaults off** (`voice_skip_while_gaming`), named to the user, and one line to flip back. Keep the probe able to fail open (a missing `nvidia-smi` must never silence the voice), and use it only to *explain* a slow reply.
- **Synthesis can *fail*, not only slow down, when the card is full — retry once, then fall back to text.** With a game (or another service) holding the VRAM the wrapper exits non-zero (`CalledProcessError`) and the reply quietly drops to text; a short pause plus one retry clears the transient OOM/timeout cases and is cheap enough to always do.
- When voice gets flaky, list the GPU's *other* consumers before changing any bridge code: `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader`. On a small card (8 GB) a stray ComfyUI or other inference service is frequently the real thief, and closing it is what the user actually wants — offer that instead of re-tuning timeouts.
- The synthesis call must be the *same* wrapper the Hermes TTS command provider uses (see the `voice-cloning` skill), otherwise the chat voice and `text_to_speech` output drift apart.
- Ask before making voice unconditional in group chats: any member can then talk the bot out of it ("别发语音了") in ordinary conversation, and the choice the user made gets silently reversed. Private-chat-only, or "voice while the owner is present", is usually what the user actually wants.

## Outbound reply hygiene
- **Sanitize every reply in the one send helper: strip `data:…;base64,…` URLs and drop whole lines that are ≥120 chars of base64.** An image posted in a group is fed to the model as a data URL; when the model echoes that string back instead of talking about the picture, the bridge splits it as if it were prose and posts ~150 chunks of "乱码" into the group (the chat API rejects most with `400`, so the log also storms). The user reports garbage, not a stack trace — clean the text where every send passes: data URL → placeholder, base64-only line → drop, remainder → truncate.
- **Cap the chunks and abort on repeated failure.** Send at most ~6 chunks per reply and `break` out of the loop after 2–3 consecutive send failures. An uncapped split turns one bad string into an unbounded retry storm against the chat API.
- Mirror the same rule into the per-channel instructions ("绝不要把图片的 base64 / data: 开头长串复述出来") so the prompt and the sanitizer defend the same seam.
