# QQ <-> Hermes bridge (NapCat/OneBot -> Hermes api_server)

Runtime pieces: bridge `$HERMES_HOME/scripts/qq-bridge.py`, config `$HERMES_HOME/qq_bridge.json`,
session map `$HERMES_HOME/qq_bridge_sessions.json`, log `$HERMES_HOME/logs/qq-bridge.log`.
It consumes QQ events, routes each sender to a Hermes profile (owner -> `default` full tools;
everyone else -> a guest profile whose `platform_toolsets.api_server` is reduced, e.g. `[web]`),
and pushes the reply back through the AstrBot OpenAPI. AstrBot/NapCat platform internals live in
the `astrbot-plugin-ops` skill; this one is the bridge itself.

## When to Use
- QQ messages get no reply, the wrong persona answers, group behaviour or per-sender permissions are wrong.
- Changing what the bridge feeds Hermes (images, quoted messages, forwarded chat records) or how turns are queued.
- A QQ message needs context to answer it — what the chat said around it, what a shared file/card was, whether anything is pending on the bot — pull that over the WS action channel (see Debugging) instead of guessing.

## Saved-account login recovery

When `6099` is up but `3001` is down, query NapCat's login status before restarting. Read the installed `napcat.mjs` for the current API contract. With the WebUI token read internally from `config/webui.json` (never print it), POST `/api/auth/login` with `hash=sha256(token + '.napcat')`; retain returned `data.Credential` privately and use `Authorization: Bearer ...`. POST `/api/QQLogin/CheckLoginStatus` and `/api/QQLogin/GetQuickLoginList` — the list's `data` is a plain array of uin **strings** (e.g. `["1568468","1150111337"]`), not objects: parse strings and dicts defensively, pass the bot's exact uin, and never pick the owner's personal account that sits in the same list. If the phase is `waiting_qrcode` and the expected bot account is saved, POST `/api/QQLogin/SetQuickLogin` with its exact `uin` before asking for a QR scan. Never select the owner's personal account. Read status back: require `isLogin=true`, `coreReady=true`, and verify identity via OneBot `get_login_info`, then bridge `/health.ws_connected`. If saved login fails, use the QR flow; never loop login attempts or bypass a verification challenge. Verify a recovery test send over the action channel: `send_private_msg` can answer `status: ok` **without** a `message_id`, so read back `get_friend_msg_history {user_id, count}` and match the text — a missing id is not a failed send (this proves transport, not an LLM round trip).

**When the saved list is empty, go straight to the WebUI QR API instead of driving the QQ client's login window.** `POST /api/QQLogin/GetQQLoginQrcode` (same auth headers) returns `data.qrcode` — a `https://txz.qq.com/p?k=…` link that rotates about every 2 minutes — and `POST /api/QQLogin/RefreshQrcode` returns the current one under `data.qrcodeurl`; render the link to a PNG with any `qrcode` library and hand that image to the owner/client. **Send the account QR image, not the WebUI link, when someone remote has to log the bot in**: the WebUI's own login page carries a *different* QR (「Web Login」) and that is the one people scan by mistake — it leaves them parked at 「二维码已扫描，等待手机确认…」 with nothing happening. `CheckLoginStatus.loginPhase` tells the two apart: `waiting_qrcode` = nobody scanned the bot QR yet, `qrcode_scanned` = scanned but the phone never tapped 确认登录 — ask them to tap it, and re-send a freshly refreshed QR rather than waiting the old one out (it rotates every ~2 min). Driving the client's saved-account window is a trap: it is Chromium, a **background** `capture(mode='som')` returns **0 elements**, and after a foreground click the AX tree appears — but clicking 登录 starts logging in *every checked account* (two went to 「登录中…」 together), disables the button, and hangs at 「登录中…」 indefinitely. **Identify whose window you are driving before touching it:** the picker you reach with `list_windows` is frequently the MAIN install's login window (it lists the owner's personal accounts and its 登录 binds all of them), while a copy launched with its own `--user-data-dir=<copy>\data` keeps its own store — the failure is "wrong installation's window", not a shared account store. Resolve the window's PID to `ExecutablePath`/CommandLine (`C:\Program Files\Tencent\QQNT\QQ.exe` = main, `Apps\QQ-clientN\QQNT\QQ.exe` = that copy) and log the bot in through the COPY's WebUI QR instead. Expect `GetQuickLoginList` to come back `[]` with phase `waiting_qrcode` after a QQ-client restart or reboot — the saved-login state is gone and a rescan is the only way back, so generate the QR in the same turn rather than promising "it will auto-login".

**A guest who is not at this machine scans through a tunnel, not through the owner's browser.** The WebUI login page takes the instance token (`config/webui.json` → `token`; join it as `/webui?token=<tok>` so one link carries both); to hand that page to a remote person run a Cloudflare quick tunnel against the instance's WebUI port: `cloudflared tunnel --url http://127.0.0.1:6100 --no-autoupdate` started hidden with its stderr redirected to a file — the `https://<random>.trycloudflare.com` URL appears there within ~10 s. Verify from outside before sending it: `curl -L "https://<host>/webui?token=<tok>"` must return 200 with the SPA shell (~1.3 KB; `/webui` alone answers 301 → follow it). Ship `<tunnel>/webui?token=<tok>` plus the bare token (the page may still ask for it), and state the two caveats every time: the link is **full control of that bot** (only to the named person) and a quick tunnel is ephemeral — a machine/tunnel restart changes the URL. When GitHub download is blocked, `https://gh-proxy.com/https://github.com/...` served the cloudflared release while the direct URL through the local relay stalled at 0 bytes. **Check that a fresh quick tunnel's hostname actually resolves before sending it** — some come back «created + connection registered» yet the hostname is NXDOMAIN and every request answers `000`/`502`; that tunnel is dead, kill the process and start a new one rather than debugging the app behind it. Several quick tunnels run side by side (one per bot instance, each pointed at its own WebUI port); every new start mints a new hostname, so never reuse a link across instances and keep the port↔link↔token mapping straight while several clients are being onboarded at once.

## Second account / client profile onboarding

完整流程见 hermes-messaging-gateway 技能里的 multi-account-onboarding 参考文档；桥接侧要点：

- 每个 QQ 号 = 一套 QQ 客户端实例 + 一份 NapCat.Shell（NapCat 官方 issue #741/#743 明确不做单实例多账号）；端口全部错开：OneBot WS 3001→3011、WebUI 6099→6100、桥接 8790→8791。
- 桥接已有 `/p/<profile>` 路由（`_profile_base` + `guest_profile`）：第二实例把 `guest_profile` 设为目标档案（如 `client1`）、`owner_qq=[]`，全部消息就都走该档案。配置路径目前写死 `$HERMES_HOME/qq_bridge.json`，跑第二实例前加环境变量覆盖（日志/会话映射也要各自分开）。
- 目标档案必须补 `API_SERVER_KEY`（同主档案值），否则 `/p/<profile>` 拒绝服务；`hermes profile create --clone` 会把主人的 `DEEPSEEK_API_KEY` 等 provider key 一起复制过去——客户档案必须删掉、换客户自己的 key，否则账单记到主人头上。
- 唱歌/画图是桥接直接 spawn sing_service/image_service（共享本机 GPU 与一次一首的锁），不需要给该档案开 terminal 工具；多人同时点单会排队。
- **`--user-data-dir` 必须隔离，否则会把正在跑的机器人踢下线**：QQNT 副本默认沿用 `%APPDATA%\Roaming\QQ`（实测两个客户端共用同一会话目录 → 机器人 QQ 被顶掉，6099 和 3001 一起消失）。启动器给副本传 `--user-data-dir="<副本目录>\data"`（NapCatWinBootMain 会把多余参数转交给 QQ），**启动后用 `Get-CimInstance Win32_Process` 看副本进程的 CommandLine 核实确实是新目录——参数没被转交前绝不能让客户扫码登录**（登录动作可能再次挤掉机器人）。恢复被踢的机器人：`taskkill /F /IM QQ.exe` → `explorer.exe …\gateway-service\NapCat.vbs` → WebUI 快捷登录机器人 uin。
- **副本的 `loadNapCat.js` 是硬编码绝对旧路径**：它只有一行 `await import("file:///…/原目录/napcat.mjs")`，不改的话副本实际跑的是**原版 NapCat 代码**（二维码写回原目录 `cache/qrcode.png`、配置疑似两个实例共用）。复制后第一件事改成副本自己的 `napcat.mjs`；验收信号 = 新实例的二维码出现在副本目录而不是原目录。
- 复制后先改副本 `config/webui.json` 顶层 `port`（6099→6100）再启动；`onebot11_<uin>.json`（WS 3011）要等客户 QQ 登录、拿到 uin 后再建。健康判断按端口归属 + 每实例自己的 boot log，不要用「QQ 进程总数」（两个实例混在一起计数）。
- 第二实例的完整复制/隔离/启动/验收配方（含核对清单）：`references/second-qq-instance.md`。

## Event feed
- **Subscribe to NapCat's OneBot WebSocket server (`ws://127.0.0.1:3001`), never rely on NapCat's HTTP report client.** The HTTP client can be `enable: true` in `onebot11_<uin>.json` and still post nothing at all — the WS server is the feed that actually delivers. Keep the HTTP `/qq` endpoint as a secondary path, deduped by `message_id`.
- Filter at the feed entry: only private messages and group messages that @-mention the bot spawn a worker thread; count and periodically summarise the ignored ones. Otherwise every line of chatter in a dozen groups spawns a thread just to be dropped.
- **Blocking a person entirely is a config list, not a personality instruction.** `ignore_uins` in `qq_bridge.json` (default `[]`) makes the bot fully silent to those QQ ids — enforced in four places: the DEFAULTS key, the `should_handle` pre-filter, the `handle_event` entry (logs `[skip] 忽略名单 uin=…`), and the `handle_notice` friend greeting (a blocked user gets no 「你好呀」 either). Add/remove ids and restart the bridge; the config file is the source of truth for who is currently blocked. Table-test in-process before restarting: blocked private + blocked group-@ → `should_handle` False, owner/other senders → True.
- Group replies fire only on an @-mention: an `at` segment whose `qq` equals the bot uin, `[CQ:at,qq=<bot>]` in `raw_message`, or a configured wake prefix. The reply UMO is the group, the session key is `(profile, group, member)` — never one shared group session, or a guest rides the owner's full-tool session.
- **A wake *word* anywhere in the text is a first-class trigger, not just `@`.** The user's rule: in a group, saying the bot's name (default `大肥鱼`, config `group_wake_words`) counts exactly like an @-mention. Match the message *text* case-insensitively as a substring **in addition to** the `at` segment and the prefix list — a prefix-only check misses "帮我问下 大肥鱼 这事儿", and the user will report the bot as deaf. After the event feed connects, call NapCat `get_login_info` once and merge the bot's own current nickname into the wake list, so renaming the bot in QQ keeps the trigger alive with no code change.
- **Route `notice` and `request` events in *every* ingress, not just the WS feed.** Friend-added notices arrive on the same feed as messages, and the bridge has two entry points (the WS loop and the HTTP `/qq` endpoint). Adding the branch in one and testing through the other looks exactly like "the feature does not work": the POST still returns `{"status":"ok"}` and nothing is logged, because the pre-filter drops non-message events silently. Factor the handling into one function, call it from both ingresses, and log a line for every dropped event so a silent no-op is visible next time.
- **Decode inbound bodies strictly in BOTH ingresses, with a GBK fallback — the HTTP ingress is lossy today.** `/qq` does `raw.decode("utf-8", "replace")`, so an event body that is not UTF-8 (a GBK-encoded poster, a hand-rolled test harness) becomes `U+FFFD`-laden text and the destroyed bytes are gone for good; the WS feed hands you a `str` already decoded, so a `U+FFFD` there came from upstream (sender or NapCat), not from the bridge. Pattern: try `raw.decode('utf-8')`, on `UnicodeDecodeError` retry with `gbk`, and log which branch was taken. Recovering a message that already arrived mangled — and proving the reading byte-for-byte — is `references/inbound-text-encoding.md`.

## Concurrency
- **One turn at a time per chat.** Hold a per-chat lock for the whole turn. Two messages that arrive together for a chat with no session yet otherwise both `POST /api/sessions`; Hermes rejects the duplicate with `400`, and the loser posts "HTTP Error 400" into the user's chat.
- Retry session creation once with a different title, and re-read the session map under the same lock before creating — a lost race still happens around restarts. The duplicate-title rejection is `400` whose body names the offender (`invalid_title` / `... is already in use by session <sid>`): read that id out of the error and choose deliberately — reuse it (keeps history) or generate a suffixed title (intentionally fresh, e.g. after clearing a polluted session) — rather than blind-retrying.
- Cap queued turns per chat (drop + log when over the cap) so a burst cannot pile up forever.
- Write the session map atomically (temp file + `os.replace`) under a lock: several workers finish turns simultaneously and a plain rewrite corrupts the JSON.
- Serialize sends per chat so multi-chunk replies cannot interleave, and serialize the shared NapCat action socket.
- **The ack timer is a noise trap — leave it off.** A 「收到，我在处理」 broadcast sent from a `threading.Timer` (~25 s) was meant to keep a long turn from looking silent, but when the user fires several messages in a row every queued turn fires its own identical ack (each one also drags along that turn's meme decoration), minutes apart — he reports 「它一直在无限回复」 and the bot reads as stuck in a loop. Keep `ack_after_s` at 0 **in the running `qq_bridge.json`** — an absent key silently falls back to the code default where the timer lives, so the noise returns whenever the file is rewritten; verify the effective value by importing the module and printing `CONFIG['ack_after_s']`. If an ack is ever truly wanted, cap it to one per chat per several minutes, never one per queued turn. 这个禁令只针对**每回合自动计时**的那种：当你自己（agent）准备花好几分钟办用户随手提的一件事时，先手打一行「收到，在查」再埋头干——用户会在一场十分钟的静默审计中途 ping「怎么没回复我」，只让迟到的报告落地会被当成死机。

## Shared group memory (auto-compressed digest)
- **Sessions are per (profile, group, member) — by design — so no two members' turns share group context**: the bot answers each regular as if the group's recent story never happened. Do NOT merge sessions to fix it (a guest would ride the owner's full-tool session); inject a shared digest instead.
- Pipeline: a cron job every ~3h reads the bridge log's recent `group <gid>` lines, distills ≤~350 字 (hot topics / regulars / standing rules / ongoing storylines, written as notes-to-self — not a transcript recap) and overwrites `$HERMES_HOME/cache/qq_group_digest_<gid>.md`; `ask_hermes` appends that file (capped ~1200 chars) to the `instructions` of every request whose chat_key starts with `g` (`_group_digest()` helper). Private chats are unaffected.
- Keep the compress job `deliver=local` — the digest must never land in a chat — and have the injected header tell the model not to mention 「摘要」 or read it aloud.
- Read digest log windows with the log's real encoding, and decode **line by line — the file is mixed-encoding, not uniformly GBK.** `grep` over it even reports `Binary file matches`, and one run's `[recv]` line renders as `0张图` while the next renders as `0��ͼ`: some writers log UTF-8 and others the ANSI code page. Decoding the whole file with either codec corrupts the other half, and `Get-Content -Encoding Default` mangles the UTF-8 lines the same way. Working recipe (verified): a Python script reads the file as **bytes**, splits on `b"\n"`, filters `b"group <gid>"`, then decodes each line `try utf-8 except UnicodeDecodeError -> gbk`, writing the result to a UTF-8 file in the scratch dir and printing it from there. Never summarise from a mojibake view — read the QQ nicknames from `$HERMES_HOME/qq_bridge_identities.json` (`groups` / `users` id→name) and cross-check `$HERMES_HOME/cache/qq_user_memory/<uin>.md`, which already carries each regular's traits, instead of guessing who is who.
- Symptom → check: 「它记不住群里的事」 → look at the digest file's mtime / the cron's last run before touching sessions or instructions.

## Long turns
- Set the per-request timeout above the longest plausible task (30 min here), not a transport default — a QQ task turn routinely runs for minutes.
- **The runtime `qq_bridge.json` overrides the code `DEFAULTS`, so read the JSON value before debugging a threshold.** A tuning value left in the code is inert once the file carries that key: the per-request timeout read `1800` in `DEFAULTS` while the live file said `300`, so every multi-minute turn (song search → download → ffmpeg) died as `Hermes 这边出错了：timed out` while the code looked correct. Same trap as `group_rate_limit_s` — change both places, and when a threshold misbehaves, grep the JSON first.
- **A helper the bridge spawns must be launched with an interpreter that has the bridge's own deps.** The send helpers import `websockets`; pointing a spawned service at a separate project venv made every send fail `连接失败：No module named 'websockets'` and return `None`, so the reply quietly fell back to text while the log still looked alive. Choose the child interpreter deliberately (config key), probe it once (`python -c "import websockets"`), and send the child's stdout to its own log file so a silent child is visible. **Environment rotation adds a second form of this failure:** after an update ships a new `environments/<hash>` venv, the *running* bridge keeps spawning children with its now-stale `sys.executable`, and the old env's `Lib/site-packages` may have been emptied — same `No module named 'websockets'`; and because images must go over the NapCat WS while text can fall back to the AstrBot OpenAPI, only *image* sends go dark while the bot still talks. Fix: relaunch the bridge on the current env, or at least re-check the launch/restart scripts' hard-coded interpreter path — and for an **instant repair with no restart**, recreate the old env's emptied `Lib/site-packages` and copy the missing package over from the current venv (pure-Python `websockets` copies fine). **Identify the interpreter from `CommandLine`, not `.Path`:** `Get-Process -Id <pid> | Select Path` and Win32_Process's `ExecutablePath` both report the base exe (a venv python is only a launcher), which can point you at a python the bridge never uses; `Get-CimInstance Win32_Process -Filter 'ProcessId=<pid>' | Select-Object CommandLine` shows `"…\installs\<install>\environments\<hash>\venv\Scripts\python.exe" -u scripts\qq-bridge.py` — that venv is what children inherit as `sys.executable`. Install with `uv pip install --python "<native C:/ path>" …`: a Git-bash `/c/...` path makes uv answer `No virtual environment or system Python installation found`. **Ship the durable fix instead of chasing interpreters:** keep a copy at `scripts/_vendor/websockets` and add a try-import at the top of `qq-bridge.py` that prepends `_vendor` to `sys.path` on `ImportError` — the bridge and every child that imports it then works on any interpreter; verify by running the module with `-S` (site-packages disabled simulates the dependency being stripped) and asserting `websockets.__file__` contains `_vendor`. Prove the fix with a real `send_image(umo, path, caption)` from that interpreter: it doubles as recovery — a picture that rendered but could not be sent is not lost, and the retry delivers it.
- **A client-side timeout does not stop the server-side turn.** Hermes keeps running and stores the final assistant message in the session; the user just never sees it. Recover by reading the session's last non-empty assistant message and posting it to the chat, with one line saying the earlier timeout notice was a false alarm.
- Detect "turn finished" from the session itself, not from a status field: `ended_at` stays `null` for api_server sessions, so treat a non-empty final assistant message that stopped changing for ~2 polls as done.

## Images, quoted and forwarded content
- `POST /api/sessions/<id>/chat` accepts a multimodal `message`: a list of `{"type":"text","text":...}` plus `{"type":"image_url","image_url":{"url":"data:image/png;base64,..."}}` parts. The main model reads images natively — no separate vision provider needed. (`_normalize_chat_content`, the text-only flattener, is *not* the parser this endpoint uses; do not conclude from it that images are unsupported.)
- Resolve an image segment in this order: local `file` path (handle `file://`) -> `url` over http(s) with a browser-ish UA -> NapCat action `get_image` with the file id as the last resort. Then sniff the MIME from the file header, not the filename: QQ stickers are GIF bytes under a `.png` name and CDN URLs have no extension.
- Fetch that `url` through a **proxy-free opener**, not the ambient environment: QQ image URLs are Tencent CDN hosts that answer directly, while the default opener on a host running a local accelerator tries the accelerator first and dies `WinError 10061` as soon as the user turns it off (`[img] 下载失败` in the log). Keep one module-level `urllib.request.build_opener(urllib.request.ProxyHandler({}))` and use it for the image fetch — it does not depend on what the environment happens to hold.
- **A size cap sits in front of every fetch and exceeding it drops the image silently.** `_img_limit()` reads `max_image_bytes` (default `5_000_000`) from `qq_bridge.json`, and the reader/downloader stop at `limit + 1` bytes, so a multi-MB sticker (a phone GIF is routinely 5–7 MB) is discarded with only `[img] 拿不到图片内容，跳过` in the log and `N张图: 0` on the `[recv]` line — the turn still runs, so the model answers "你没发图" while the URL itself downloads fine by hand. Read the `[recv]` line's image count as the ground truth for "did the model see it", raise the runtime JSON key (the file wins over `DEFAULTS`) and restart the bridge; do **not** go fixing the fetch path.
- **An image the bridge dropped is still recoverable by hand — replay the path it would have taken.** `get_group_msg_history {group_id, count: 15}` returns recent messages *including* their `reply` segments; a `reply` segment only carries an id, and that id is the **quoted** message, so `get_msg {message_id: <reply data.id>}` yields the real `image` segment with its CDN `url` — which is where the picture actually lives when the sender answers by replying with a sticker. Download it through the proxy-free opener, and for an animated sticker open it with PIL and paste frames `0, n/2, n-1, …` into one montage PNG before looking: a speechless 75-frame GIF shows nothing legible in a single frame. Vision sees the montage natively, so this costs one look and lets you answer the user in the same turn instead of asking them to resend.
- An image-only message must still produce a turn — fall back to a text part such as "（对方发来图片，没有文字，请看图回应）".
- Parse `reply` (quoted message) and `forward`/`node` (chat-record card) segments, fetching `get_forward_msg` and flattening its text+images. Unparsed segments make the model answer "you sent nothing", which reads as the bot being broken.

## NapCat action channel
- Keep ONE long-lived WS to NapCat and match responses by an `echo` id through a waiter map, instead of a fresh WS per action (each image fetch otherwise pays a handshake).
- Liveness check: `ws.protocol.state` is an IntEnum, so `str(state)` is `"1"`, not `"OPEN"`. Compare `getattr(state, "name", ...)`. A substring check on the string silently reconnects on every call.

## Keeping it running (must outlive the gateway)
- **After a reboot, if `3001` is dead but QQ.exe processes exist, the client is running un-injected — re-inject by hand.** `taskkill /F /IM QQ.exe` then `Start-Process 'C:\Users\32672\Downloads\NapCat.Shell\_hermes_start.cmd' -WindowStyle Hidden` (that .cmd sets the four NAPCAT_* env vars; calling `NapCatWinBootMain.exe` bare dies in seconds, and the shipped launchers want admin/`pause`). Launch it detached and **never wait on it in the same call** — the boot main stays attached, so a foreground terminal run times out and an in-process `subprocess.run` hangs for minutes; "the launch call did not return" is not "the injection failed", so verify by probing the ports instead. **"Detached" must also survive the agent's own terminal: children spawned by a tool call are reaped when that call returns, so a `Popen` / `Start-Process` from the agent shell dies before it injects** (no error, no log line — a silent no-op). Hand the launcher to the shell instead — `explorer.exe "…\gateway-service\NapCat.vbs"`, or a one-shot scheduled task — then verify it actually ran from the launcher's own line in `logs/startup-vbs.log` **and** the ports coming up; neither alone is proof. **Never call a VBS that still contains `WScript.Echo` via `wscript.exe` from a shell — the Echo opens a modal dialog and the call blocks forever** (measured: 300 s timeout + orphaned popup). The gateway-service startup VBS are all Echo-free now (each appends to `logs/startup-vbs.log` under `On Error Resume Next`) — write any new one the same way, and test one with `cscript //nologo <x>.vbs` instead of `wscript`. WebUI `6099` answering within ~1 min = injection took. **The QQ process count is not login evidence**: a client parked at the login screen runs processes while `3001` stays dead and `cache/qrcode.png` keeps being rewritten — that combination means "waiting for a scan", and only the scan (or an auto-login) brings `3001` up. Fresh `cache/qrcode.png` = session expired → copy it **immediately before sending** (it rotates ~every 2 min), send the PNG to the owner over WeChat and note 「过期喊我再发一张」; `426` on `3001` = the OneBot listener is up (loads only after the account is online).
- **Never start the bridge from the agent's own terminal and call it persistent.** A helper launched there is a child of the gateway process tree, so `hermes gateway restart` takes it down with it and QQ silently stops answering — start it detached through a hidden `wscript.exe` launcher (recipe, recovery layers and verification in `references/bridge-operations.md`).
- Give the bridge a single-instance guard (probe the listen port, log, exit) so the login item, the watchdog and a manual start cannot stack two bridges on one port. The guard still races (two starts in the same second both see a free port): make the loser exit on the bind error instead of running on, and when diagnosing, check *which* PID owns the port (`netstat -ano | grep ':8790 .*LISTENING'`) against the PID whose stdout the launcher redirected — an orphaned second instance eats the same events, so the log and the live behaviour disagree (the log stops growing while `/health` keeps advancing `last_event_at`, and the python count exceeds what a single healthy launch produces: one launch already yields a `cmd` wrapper plus a **parent/child python pair**).
- Keep two recovery layers: a Startup-folder login item for reboots, and a repeating scheduled task that starts the bridge whenever the port is not listening. Verify by killing the bridge and watching the watchdog bring it back — do not assume the mechanism fired.
- **Strip the host proxy out of the bridge's own loopback calls.** On a machine running a local accelerator (Clash/V2Ray-style, `127.0.0.1:7890`) a bridge started the usual way inherits `HTTP_PROXY`/`HTTPS_PROXY` without `NO_PROXY`, and then routes *loopback* through the proxy too: `urllib.request.proxy_bypass('127.0.0.1:3001')` returns `False`, so `websockets`' default `proxy=True` connect goes to the accelerator and dies `WinError 10061` the moment the user quits it. Fix it inside the process at startup — force `127.0.0.1,localhost,::1` into `NO_PROXY` **and** `no_proxy` (covers the urllib calls to the api_server and the bot framework), connect with `proxy=None` (retry the plain call on `TypeError` for older `websockets`) — because a launcher or scheduled task inherits whatever the host has today. Belt and braces for the bridge's own HTTP calls (api_server, bot framework, image fetch): keep one module-level `build_opener(ProxyHandler({}))` and use it everywhere local/domestic, so the fix does not depend on the environment at all. Reproduction and the exact snippets: `references/bridge-operations.md`.
- Monitor the **feed link**, not just your own port. The bridge can be alive, listening and reconnecting every 5 s while NapCat's OneBot WS (`3001`) is down — the user then reports "QQ 收不到消息" while every probe of the bridge looks healthy. The feed cannot be relaunched by a script (it lives inside the QQ client) — **but a QQ-client restart can, and since 2026-10-13 the watchdog does exactly that instead of only alerting** (see the auto-heal bullet below; manual cure is a QQ-client restart (unless the hook has gone stale against an updated QQ — third case below). Three causes produce this same log, so discriminate before acting with `curl -s -o /dev/null -w '%{http_code}' --noproxy '*' http://127.0.0.1:3001/`: `426` (an HTTP request to a WS endpoint) means the feed is healthy and the failure is the proxy case above; no answer means the port is not served at all — then separate **client down vs account not logged in**: NapCat's WebUI port (`6099`) answering while `3001` is dead, plus a freshly written `NapCat.Shell/cache/qrcode.png`, means the bot account is sitting at a login QR waiting for the owner to scan. The OneBot listener is configured *per account* (`onebot11_<uin>.json`) and only loads once that account is online, so a logged-out account produces exactly "6099 up, 3001 gone" — that is not a config regression, and do not go hunting in the config for it. **Both ports dead with QQ itself exiting seconds after launch is the third case: the NapCat hook no longer matches the installed QQ.** QQ updates itself in the background and the hook is packed per QQ build, so after an update QQ starts under `--enable-logging`, the boot main resumes it, and it dies — `NapCatWinBootMain.exe` prints its argv block and `Process exited.` within seconds, the QQ process count returns to 0 in under ~10 s, and neither port ever listens. Read the two versions instead of guessing: the build the hook was packed for is `version` in `NapCat.Shell/qqnt.json`; the installed one is `(Get-Item 'C:\Program Files\Tencent\QQNT\QQ.exe').VersionInfo.FileVersion` (and a staged `<old>-<new>.zip` under `QQNT/versions/` means another update is pending and will break it again). On a mismatch the QQ-client restart above does nothing — update `NapCat.Shell` to the release whose notes name the installed QQ build. Back up `NapCat.Shell/config/` first (it holds the login session, e.g. `napcat_<uin>.json` / `onebot11_<uin>.json` / `webui.json`), overlay the new release's files, keep `config/`, then re-inject. Four things that cost a full round of false leads:
- **Verify the downloaded release before extracting.** `curl -C -` on a flaky link leaves a file that `tar -tf` lists fine but that fails mid-extract (`ZIP decompression failed` on `native/napi2native/napi2native.darwin.x64.node` — a macOS binary, so it looks unrelated to Windows). Compare `sha256sum` with the asset's `digest` field from the GitHub API and re-download whole if it differs; do not trust a resumed download.
- **Re-inject through the launcher's environment, not by calling `NapCatWinBootMain.exe` directly.** The boot main reads `NAPCAT_PATCH_PACKAGE` / `NAPCAT_LOAD_PATH` / `NAPCAT_INJECT_PATH` / `NAPCAT_MAIN_PATH`, which the launcher sets before it execs — invoked bare, QQ is resumed and then dies within seconds exactly like the version-mismatch symptom, so you "confirm" a theory you have already fixed. Set all four (or call the launcher) and the same binary boots a healthy QQ.
- **Admin is not required — but the shipped `launcher.bat` insists on it.** It checks `net session` and re-launches itself elevated through `launcher-elevate.ps1 ... wt.exe`, which an agent session cannot approve (no UAC prompt ever renders). `launcher-user.bat` is the same injection without the check and works unelevated. Put the four env vars + the launcher call in your own no-`pause` `.cmd` (the shipped scripts end in `pause`, which hangs forever in a background/non-interactive run) and drive that from the VBS/Startup item; do not point the login item at `launcher.bat` or every boot waits on a UAC dialog nobody answers.
- **Never let NapCat's log pipe inherit a console that will go away — `EPIPE: broken pipe, write` in a QQ dialog is that failure, not a NapCat crash.** The injected NapCat writes its log through a pipe chain (QQ stdout → `\\.\pipe\NapCat_<pid>` pumped by `NapCatWinBootMain.exe` → *its own* stdout). Start the chain from a captured/agent terminal and the pump's stdout **is** the tool's pipe: when that call ends (or the process is reaped), the reader vanishes, the next log write throws an uncaught exception in QQ's main process, and a modal `A JavaScript error occurred in the main process — Error: EPIPE` box pops over whatever the user is doing. It reads as a crash — it is not: the bot keeps answering, `3001` still returns `426`; only the log path is dead, and the box can recur on later writes. Read the stack (it names `napcat.mjs` and a `SyncWriteStream`). Cure: a clean re-inject through the hidden launcher after killing QQ **and** the stale `NapCatWinBootMain` pumps; going forward start it only via the Startup item / VBS / scheduled task, never from a tool shell.
- **NapCat 的 QQ 主窗口平时缩在托盘，`list_windows` / `focus_app` 都找不到它 —— 要用它（人工核对 UI、录演示素材）走 `MainWindowHandle`：**
  `Get-Process QQ | Where-Object { $_.MainWindowHandle -ne 0 }` 挑出真正在跑的那个客户端（其余 QQ 进程句柄全是 0），
  再 P/Invoke `ShowWindow(h, 9)`（SW_RESTORE）显示、`MoveWindow` 定位；之后 cua-driver 就能按 `window_id` 抓到它
  （`window_id` 与 Win32 句柄同值）。**绝不要为了「打开 QQ」再跑一次 `QQ.exe`** —— 那会弹一个登录窗，列出本机保存过的
  账号（可能是主人自己的号），既不是你要的客户端，还有被误登录的风险。窗口位置会自己贴回左上角（MoveWindow 不一定生效），
  录屏/截图前先 `GetWindowRect` 量出真实矩形再算区域。
- **录 QQ 界面当素材时只框消息列，录屏要在叫用户开始之前就启动。** 左栏会话列表、右栏成员名单（群名 + 几十个昵称）
  都在隐私红线里，框窄一点就少打一次码；而先开录、再告诉用户「开始发吧」能把用户读消息的时间一起录进去，
  剪掉即可 —— 反过来（等用户动了才开录）第一句指令和它的等待时间全会漏掉。
- **A re-inject may land on the login screen even for an account that was online a minute earlier — say so before you do it, and be ready to hand over a QR within seconds.** Killing QQ drops the saved session often enough that "it will auto-login" is a promise you cannot make: after the re-inject, `6099` answers while `3001` stays dead and `cache/qrcode.png` keeps being rewritten = waiting for a scan (copy that file immediately — it rotates ~2 min — and send it with 「过期喊我再发一张」). Also expect the **first turn after a reinject to be cold and slow** (~1 min vs the usual 5–6 s: session + TTS rebuild), and remember that messages sent while `3001` was down were never delivered and cannot be replayed — the user may ping 「怎么不说话」 mid-gap, so before investigating anything, pull `get_group_msg_history` and check whether the reply already landed (and when).
- **`3001` 自动自救：`qq-bridge-watchdog.py` 自己会跑 `NapCat.vbs`。**
  触发条件必须是**双端口都挂**：连续 2 轮（≈20 分钟）`3001` 不在听 **且 `6099` 也不在听**——那才是「NapCat 整个没加载（未注入的 QQ 客户端）」。只有 `6099` 在听（多半是掉登录停在扫码页）仍**只告警**：重启修不了掉登录的账号。
  护栏一条都不能少：轮数**只在 `main()` 里每轮 +1**（绝不能放进可能被调多次的辅助函数——2026-10-13 19:29 一次运行里它连记了「连续 2 轮/3 轮」两次并两次"启动"，而端口其实是好的；当时没出事全靠 NapCat.vbs 自带的端口检查兜底）；**动手前 3 次探测复核**（这层是让假阳性无害的关键）；30 分钟冷却；每日封顶 3 次；进程内只动一次手。
  进程内验证矩阵（monkeypatch `listening` + `subprocess.Popen`，9-10 个用例）：正常 / 只挂1轮 / 6099在听 / 真挂→动手 / 冷却期 / 试满封顶 / 跨天重置 / **假阳性复核拦下** / **同进程二次调用拦住** —— 全过才允许提交。
- **NapCat ships its own GitHub mirrors** in `napcat.mjs` (`gh.5050net.cn`, `gh.inkchills.cn`, …) for when github.com is unreachable. They are rate-limited hard (429) in practice, so prefer asking the owner to switch the local accelerator back on — with it on the same download went 5 MB/s vs ~30 kB/s direct. When you do read that file, read it properly: listeners nest under `network.websocketServers` / `network.httpClients`; a top-level `websocketServer` lookup returns empty and sends you chasing a non-problem. Have the bridge report its own feed state in `/health` (`ws_connected`, `last_event_at`) and alarm on `ws_connected == false` — the port probe passes in the proxy case.
- The launcher must discover the interpreter (probe candidates under `installs/*/environments/*/venv` for the dependency marker) and the bridge must fall back to reading `API_SERVER_KEY` from `$HERMES_HOME/.env`: a VBS/task launch inherits no environment, and install paths change on update.
- Prove detachment from the process parents (`parent is gateway = False`), not from the fact that it started.

## Debugging
- **A bare 「X 报错」 or a screenshot means: look at the screen first, not the logs.** The user is reporting something they are looking at right now — capture it (`computer_use(action='capture', app='screen')`) or ask for the exact wording, then match it to a mechanism. Auditing logs first picks whichever line looks like an explanation and sends you off fixing a real-but-unrelated problem while the dialog the user actually meant stays unaddressed.
- Read the log with `grep -a` on the exact field (`[in]`, `[recv]`, `[send]`, `[error]`) rather than `tail -n`. A long turn pushes older lines past the tail window and "the event never arrived" is then a false conclusion.
- **Log timestamps are `[HH:MM:SS]` with no date, and the file spans days — a `grep` keyed on `^\[14:` drags in same-time segments from older days.** For "what just happened right now" read the raw tail of the file (or correlate against the message `time` epoch fields from `get_group_msg_history`); a line whose timestamp looks like it is from the future is from a past day, not a clock bug.
- Log the inbound segment kinds (`segs=['at','image','text']`) plus sender/group on every message. A silent non-reply is almost always an unparsed segment kind, not a routing failure.
- **Read the reply text, not just the send status.** When every reply the bot posts is an English provider-auth error, routing and delivery both worked — the sender's *profile* is the problem: a profile `.env` shadows the main one, so one stale key breaks that profile while the owner keeps working. Diagnose from the key tail in the provider's 401 and repair per the provider-credentials section of `references/bridge-operations.md`. **A provider outage is the same send-layer signature with a different cause:** raw fallback text lands in chat (`Model '<m>' isn't available on custom…` / `Provider said: HTTP 404 …`), `logs/errors.log` shows `API call failed … provider=<name>` in the same minutes, delivery itself was fine, and it clears on its own — wait for recovery, prove it with one live call, and do not change config or switch models mid-outage.
- **Test the routing predicate in-process before touching the live bridge.** Load the module by path (`importlib.util.spec_from_file_location`) — module level only reads config, since the server starts in `main()` — and assert `should_handle()` on synthetic events: name inside a sentence, plain chatter, an `at` segment, a private message, and (once) a near-miss like "肥鱼". Six table-driven cases catch a wrong matcher in a second, with no restart and nothing sent to a real chat. The same probe extends to whole branches: monkeypatch `_steam_now` / `ask_hermes` / the dispatch helper (`_start_singing`, the image job) with recording stubs and call `handle_event()` on a synthetic event with a **fake group id** — the game gate for song/draw orders is then provable end-to-end without a real LLM call or a live chat (the only noise is the send failing on the fake group, which the log also proves was the *only* action taken).
- **「它不回我」先查三件静默丢消息的事，再怀疑链路**：(1) `grep '\[skip\] rate limited'` —— 桥接有每成员每群的冷却窗，用户连发两句时第二条被**静默丢掉**，观感就是「不回」；把窗口压到约 1 s（`group_rate_limit_s`，运行时配置与代码默认值一起改）并保证丢弃时打日志。(2) 只有 `@` 没有文字（或只 @ 了一个表情）的消息**必须回一句**——曾经「按设计跳过」，结果就是「@ 了它它不理」被当成故障报上来（用户问「这个群你不发消息了」）。做法：内容为空但机器人被叫到时，塞一句占位文本（如「（对方只 @ 了你，没说话）」）走正常回合；只有既没被叫到又没内容的才丢。(3) 只在群里没叫到名字时才走 `已忽略 N 条无关消息` 计数——用户以为叫了名字却没被接住，就去核对他那条到底带没带唤醒词。三件都排除后才是链路层（`ws_connected`、3001、代理）。
- **重启桥接（或任何自家长驻进程）只按「监听端口的 PID」杀，且杀完必须验证真的换了进程。** 按命令行关键字杀有两种翻车方式：模式串 `CommandLine -like '*qq-bridge.py*'` 会连你自己正在执行的 shell 一起杀（它的命令行里也含这串），命令断在半路；而 `-like '*qq' + '-bridge.py*'` 会被 PowerShell 解析成 `(命令行 -like '*qq') + '-bridge.py*'`，**谁都不匹配**——杀了个寂寞：旧进程继续服务，`/health` 照样绿，你向用户汇报「已重启」而跑的仍是旧代码。**先认清正常进程形态：一次启动产出「cmd 壳 + 一对 python（父子进程、命令行相同）」——2 个 python 就是单一实例的正常样子，别把它当重复进程去「清理多余的那个」：实测杀这对里任意一个，两个一起走，等于把桥接整个停掉。** 流程：`netstat -ano | grep ':8790 .*LISTENING'` 拿端口宿主 PID（它就是这对之一）→ `MSYS_NO_PATHCONV=1 taskkill /F /T /PID <pid>` → 确认进程归零 → `wscript.exe "…\gateway-service\QQ_Bridge.vbs"` 重新拉起、等 ~10 s → 重启后**新 PID 必须不等于旧 PID**，且日志尾部出现一条**新时间戳的启动横幅**。别用 `/health`、也别用「重新 import 模块看指令文本」证明重启成功：前者由旧进程应答，后者读的是磁盘文件，不是你正在跑的那个进程。 **`/T` 会连坐杀掉桥接派生的子任务**（唱歌/生图服务都曾是桥接的子进程）：重启前先看有没有长任务在跑（唱歌查 `logs/sing.log` 与 `work/sing.lock`——被掐死的唱歌会留下孤儿锁，之后所有点歌被静默吞掉）；桥接侧新起的长子进程要用 `DETACHED_PROCESS`，重启从此不连坐。 Git-bash 下 `taskkill //F //PID` 会把 `//F` 原样传给 taskkill 并报「无效参数」；要么 `MSYS_NO_PATHCONV=1 taskkill /F /PID <pid>`，要么直接 `powershell -NoProfile -Command "Stop-Process -Id <pid> -Force"`。`restart-qq-bridge.sh` 在旧桥接还活着时会撞 `>> logs/qq-bridge.log: Device or resource busy`——脚本表面上"跑过了"，进程根本没换，别把它当已重启；按端口 PID 杀掉后由看护在 ~1~1.5 分钟内拉起，验收同前（新 PID ≠ 旧 PID + 日志出现 `[up] QQ bridge listening` 与 `[ws] connected`）。
- **An allow-rule usually exists twice; patching one copy is the same as patching none.** The ingress pre-filter (`should_handle()`) and the handler body each decide "is this message for the bot?" — a group bypass added only to the pre-filter still gets dropped by the handler's own `@`-or-wake-word check, silently, before it logs `[recv]`; the user then reports "QQ 不说话了" while every probe of the port, the feed and the profile looks healthy. Before trusting any bypass, `grep` for the other copies of the same predicate (`mentioned_bot(`, `should_handle(`, `owner_qq`) and make both call one shared predicate. Prove it by injecting a synthetic event — see the probe bullet below — not by reasoning.
- **Run in-process probes with the interpreter the bridge actually uses, not the default Hermes runtime one.** The launcher picks whichever `installs/*/environments/*/venv` carries the dependency marker, and that is often *not* the venv the gateway uses — probing with the wrong python dies in about a second (`No module named 'websockets'`, a send action returning `None`) and looks exactly like a broken bridge. Read the real interpreter off the process command line (`Get-CimInstance Win32_Process` for `qq-bridge.py`) or the launcher's discovery logic (`for p in installs/*/environments/*/venv/Scripts/python.exe; do "$p" -c "import websockets"; done` — the first that prints nothing is the right one; the venv the gateway itself runs on usually lacks it), then load the module by path (`importlib.util.spec_from_file_location` — safe, the server starts in `main()`) and call the helpers directly. This is also how to pre-warm audio: `_make_voice(text)` then `send_voice(umo, path)`, with the cached mp3's path printed for the user to play. **Call the module-level helpers directly (`napcat_call` / `send_qq` / `send_voice` / `_make_voice`); the bridge module has no `load_bridge`** — that is `sing_service.py`'s own wrapper (which also registers the module as `sys.modules['qq_bridge']`); copying its loader into a scratch script dies `AttributeError`. Prefer extending `scripts/napcat_query.py` over hand-rolling the loader again.
- Verify a fix with a real probe: post a synthetic event (`POST /qq`) using fake ids so nothing reaches a real chat, then grep the log for the `[in]`/`[recv]`/`[send]` triple.
- **A group you receive events from but can never send to is a synthetic event, not a delivery bug.** NapCat answers `retcode 1200` (`EventChecker Failed`) and the bot framework `HTTP Error 400` for `GroupMessage:<gid>` while the same send path works for real groups — that combination means the event was fabricated (a harness posting into `/qq`, a test id such as `999999901`) for a group the bot is not in. Check whether the id is even in the bot's group list (NapCat action `get_group_list`) before touching the send path; do not "fix" sends for a group that does not exist, and tell the user replies to it cannot land.
- **A garbled message is an encoding fault, not a user typo or a model failure.** Read the raw bytes of that log line with Python (`open(...,'rb')`, slice by an anchor such as the group id) instead of a text view: `U+FFFD` shows there as literal `EF BF BD`, which is how you tell "the bridge received bad bytes" from "the log itself is mangled". Then recover and verify per `references/inbound-text-encoding.md` and say which characters you inferred — lost bytes make a reading plausible, never certain.
- Identify who listens on which port from the PID: `netstat -ano | grep LISTENING | grep -E ':(3001|6185|8790|9880|8642|7899) '`, then `tasklist | grep <pid>`; `tasklist //FI "PID eq <pid>"` prints nothing under git-bash, and `powershell -NoProfile -Command "Get-Process -Id <pid> | Select Id,ProcessName,Path"` gives the exe path (`QQ.exe` on `127.0.0.1:3001` is NapCat living inside the QQ client, not a separate process to restart).
- **Group facts (member counts, who is an admin, recent messages, every group the bot is in) are one WS call away — don't reconstruct them from the bridge log, which keeps only *triggered* messages (everything else is counted, not stored). A triggered message's meaning usually sits in the untriggered chatter around it; pull the neighbourhood before answering, and fetch any shared artifact too — file segments carry their own download URL, so read the file before commenting on it.** The event socket is a full OneBot action channel: run a scratch script with the *bridge's* interpreter and connect `websockets.sync.client.connect("ws://127.0.0.1:3001", proxy=None)` (proxy trap above; the socket also pushes live events to every client, so skip any frame whose `echo` is not yours). Useful actions: `get_group_list` (each group with `member_count`/`max_member_count`), `get_group_info {group_id}`, `get_group_msg_history {group_id, count}` (includes `reply` segments, but they carry only an id — not the quoted text), `get_group_member_info {group_id, user_id, no_cache: true}` (`role` = owner/admin/member; `retcode 1200 EventChecker Failed` = that user is not in that group). 「欢迎一下新人」 arrives with no name — sort `get_group_member_list` by `join_time` desc and greet the newest join. Ready-made: **the skill ships** `scripts/napcat_query.py` (`groups` / `history <gid> [n]` / `member <gid> <uin>` / `friend <uin> [n]` / `msg <message_id>`) — it lives under **the skill's own directory** (`<skills>/productivity/onebot-qq-bridge/scripts/`), *not* in `$HERMES_HOME/scripts/`; run it with the bridge's venv python and pass the full path (or copy it into the scratch dir first). Extend it rather than hand-rolling a scratch probe. The same channel answers the private side and "is anything pending": `get_friend_msg_history {user_id, count}` (a private chat's tail), `get_group_system_msg` (pending invites / join requests), `get_doubt_friends_add_request` (friend requests, possibly stale) — empty lists mean nothing is waiting on the bot. A logged `[request]` line is informational only — the bridge never auto-accepts anything, so check those calls instead of reading the line as unhandled work.

## Dispatching heavy side tasks from chat (song orders, model runs)
- **Understand before acting: a regex hit is not an order.** 2026-10-19 主人要求「先思考识别意思再动手」——群里贴一段人设曾被当成点歌直接派单。现在点歌/画图触发前先过 `_llm_intent()`（DeepSeek，JSON 三态 sing/draw/edit + 歌名/画题，~1s）；大段粘贴（>120 字 / 多行 / 带 `**` 或 `###`）直接不触发；模型失败时短句沿用旧规则、长贴仍不触发。验收表：贴人设→全 false；「唱一首平凡之路」→sing；「画一张明日香」→draw。
- **Parse the request name with *and* without quotes.** A parser that only accepts `《...》` silently degrades 「唱一首平凡之路」 to "something random" and the bot sings the wrong song — the user notices immediately. Match the trigger, then take the remainder of the string as the name, and keep the same rule in both the bridge (dispatch decision) and the service (execution) so they cannot disagree; table-test both on the same inputs.
- **A trigger that only covers `唱…` drops the order in silence.** Users type 「点一首 X」, 「点歌手名」, 「唱《X》」, 「唱一首 X」 — a parser that recognises one and not the others returns "nothing to do" with no message and no error, and the chat simply goes quiet, which reads as the bot ignoring the order. Cover every phrasing a user has actually typed in *both* layers, log every unrecognised trigger line, and when dispatching by hand rewrite the text into a form the parser accepts (「点一首 X」→「唱一首 X」) instead of passing the raw sentence.
- **A singer name is not a song.** Library lookup by name is an unordered substring glob, so 「点一首南征北战」 happily returns any track by that artist (which one is luck of the glob order). Resolve to one concrete title before dispatching — pick the artist's best-known track, or ask in a single short line — never let the glob choose.
- **Gate a GPU/CPU-heavy side task on the owner's state before dispatching.** Read what he is playing from the bot framework's own watcher cache (`astrbot_plugin_steam_monitor`: `plugin_data/.../last_states.json` → `gameextrainfo`) — **只认主人自己的 steam id（第一个监控目标）；绝不要把「某个被监控的号在游戏里」当成「主人在玩」**：另一个被监控的号是别人的机器，它的游戏曾被算到主人头上，搞到点歌/画图一晚上全程被拦而主人压根没玩（「你只识别我游戏状态，不识别…另外一个人」）。主 id 从插件配置 `monitored_targets[0]` 解析（兜底：状态文件第一条，顺序与配置一致），只有它才继续走 Steam Web API（`ISteamUser/GetPlayerSummaries`，对应 key/steamid）兜底；答案缓存 ~60 s。 If he is mid-game, do **not** start the job: return an instruction telling the model to answer with ① the concrete game (from the probe, never invented) ② why it must wait (the job competes for the same card and would stutter his game) ③ come back in ~half an hour — one or two witty spoken sentences, composed by the model, not a template or a list.
- **一条错误的闸门提示会污染聊天会话——修好探针并不等于修好聊天。** 闸门会把「主人现在正在玩《X》」这类句子写进回合内容，它以 **user 角色消息**落进会话历史，之后模型把它当记忆反复复述，哪怕探针已修（实测：图其实一直在正常生成，聊天里却持续拿「显卡被吃鸡占着」搪塞）。指纹 + 清洗：在 `state.db`（主 profile 的 **和每个 guest profile 的**）跑 `SELECT session_id, COUNT(*) FROM messages WHERE role='user' AND content LIKE '%主人现在正在玩《%' GROUP BY 1`；`role='user'` 过滤不能省（同一串会出现在只是读了代码的 tool 输出里，包括你自己的维护会话——那些不许删），先备份 db，再删掉这些会话的 `messages` + `sessions` 行。然后给每一档指令补上「除非系统提示里明说『主人在玩/已拦下』，不许自己编显卡/游戏借口」，否则模型会自己发明这个借口。
- **Resolve the name to a concrete audio source inside the spawned service, never in the chat turn.** A chat turn that runs browser → download → convert blows the request timeout and goes silent mid-reply; the service subprocess has no such limit and logs its own progress.
- **Anonymous B站 search that actually works (no cookies, no browser).** `yt-dlp bilisearch` answers 412 and `--cookies-from-browser` is stopped by Chrome's app-bound encryption, but the plain endpoint is fine once the visitor id is present: `GET https://api.bilibili.com/x/frontend/finger/spi` → take `data.b_3`/`b_4`, then `GET https://api.bilibili.com/x/web-interface/search/type?search_type=video&keyword=<urlencoded>` with `Cookie: buvid3=<b_3>; buvid4=<b_4>`, `Referer: https://www.bilibili.com/` and a browser UA → `code:0` and ~20 hits carrying `bvid` + `duration`. Without the buvid the same URL returns an HTML page, which reads like "the search API is blocked".
- **Score the hits; never take the first one.** The top result is regularly a 「XX是什么梗」/解说 clip that would be sung verbatim. Add for 原唱/官方/MV/完整版/无损/音频/歌曲 in the title, subtract for 梗/指南/解说/伴奏/纯音乐/教程/合集/鬼畜, add for a 2:30–6:40 duration (longer is usually a compilation) and for the queried name appearing in the title, then accept only above a floor score; try keyword variants 「<name> 原唱」「<name> 歌曲」「<name> 音频」 in turn.
- **Who may order is policy the user changes — re-read it before enforcing the old one.** Orders were owner-only, then opened to **everyone** (group and private), and separately outsiders' requests for library-missing songs were allowed to auto-download **inside the singing service only** (they never get a tool or a shell). The one gate that stays constant is the owner's state: while he is in a game nothing is sung, no matter who asked. Keep the policy in config, and when it changes, fix the sentence in the skill instead of re-deriving the old rule.
- **Confirm the artifact landed by reading the chat back, with the window sized to the elapsed time.** A file-upload call returning success is not delivery: pull `get_group_msg_history {group_id, count}` and look for your own `file`/`record` segment plus its timestamp. `count` counts messages, not minutes — in a live group a fixed `count: 10` covers only the last few dozen seconds, so a check run minutes after the send sees chatter only and the delivery falsely looks failed. Size it to the elapsed span (≈30–50 for a few minutes) and match on timestamp, not on "it is somewhere in the tail".
- Run the job **detached with its own log file** and let it post its own «started / here it is» lines, so a multi-minute turn never holds the bridge's request timeout open.
- **Image orders are the same shape** (`image_service.py` next to the ComfyUI install, spawned by the bridge): the bridge only decides *whether* it is an image order and *what* the prompt is, then spawns a process that boots ComfyUI on port **8189**, generates and posts the picture back through a NapCat `image` segment (`_file_uri` again — a bare Windows path is read as a URL and fails "识别URL失败", same as `record`). NEVER reuse 8188: that is the owner's MiniMax-H3 video server, and its scripts treat "8188 answers" as "my video server is up".
- **A self-referential draw order must have the self-reference expanded before dispatch.** 「画一张本鱼」「画一个自己的样子」 extract to prompts like「本鱼」/「自己的样子」— the model has no idea who that is and renders a random stranger (measured live: the group asked 「这是什么」 about the result). `_expand_self_prompt()` in the bridge: a pure self-reference (本鱼/大肥鱼/你自己/自己…的样子) is replaced wholesale by the look description (`_SELF_DESC`), and 本鱼/大肥鱼 inside a longer prompt are substituted in place (「画一张本鱼在吃白米饭」→ description +「在吃白米饭」). Keep all three phrasings as table-test cases whenever the extraction logic changes.
- **Style/quality tags are not person names — keep a stopword set in the person-guess step.** 「blue archive, game cg, masterpiece…」 had `blue` read as a character name, so the bridge fetched a stranger's reference image and quietly turned a text-to-image order into an img2img built on it. Skip tag-like words (colors, `anime`/`game`/`cg`/`style`/`art`/quality words…) in `_guess_person`, and table-test the guess step like the rest of the matchers.
- **Alternation is ordered, not longest-match — write 「图片」 before 「图」.** `(?:图|图片|照片)` matched the short branch and left `片：一只可爱的柯基` as the prompt. Same family: `画个` consumed the noun in 「给我画个头像」 and the extraction returned empty — keep a fallback that re-reads the text after the match when stripping leaves nothing, and take the image noun itself as the prompt. When no subject is extractable at all (「画张图」, or only the trigger arrives), do not render: fall through to the model with a one-line nudge to ask what to draw — an order must say what to draw before a 30 s render is queued.
- **Two trigger tiers are what keep 「来一个笑话」 safe.** Strong: `画|绘制|生成` + measure word, or any verb + an image noun. Weak: `来|跑|整|搞|做|捏` + measure word, accepted **only when the message also carries an image noun** (图/图片/头像/壁纸/表情包) — without that, 「来一份外卖」 and 「来一个笑话」 start rendering. Add a small non-visual blocklist (想法/方案/总结/代码/故事…) so 「生成一个想法」 does not queue a 30 s render, **plus a code-creation rejection (`创建|写|生成` + `HTML|SVG|网页|小程序|代码|脚本|CSS|JS`): a request to write HTML/SVG code was matched by the verb+measure tier and dispatched as a picture — reject it so the turn falls through to the model and is answered with code**, and a negative lookbehind `(?<![在正别没])` so the narrative 「我在画图」/「别画图了」 doesn't fire. Table-test both layers on the same inputs; keep every case that ever misfired in the table.
- **A local model has no content moderation — the bridge has to be it.** What gets banned is the *account*, when hardcore output lands in a group. Gate on an explicit-term blocklist in the **bridge** (let the model compose the refusal line, 大肥鱼-flavoured) *and* in the spawned service as defence in depth — the service layer is what actually caught the first live violation, in the window before the bridge had its gate. Keep the list to **the owner's line — explicit only**: exposed genitalia / full nudity / sex acts / anything with minors (生殖器, 裸体, 不穿衣服, 做爱, 儿童, 未成年, nsfw, naked …). Ordinary 擦边 must render — 比基尼 / 三角内裤 / 泳装 / 内衣 pass, and the vague suggestive asks 涩涩 / 色图 are deliberately allowed; a gate that eats those reads as the bot being broken. This line is the owner's to move (he relaxes it, not tightens it); after any edit prove the tuple with the same in-process importlib probe the routing tests use — a table of pass/block phrases — before restarting the bridge. **Words with an innocent second sense need a context rule, not a plain list entry.** `裸露` is ordinary in mechanical/nature prompts (裸露的齿轮/电线/岩壁) and as a bare substring it refused a legitimate detailed order; gate such words by proximity to a person/body word (±a few chars, not crossing punctuation), keep strong words as substrings, and table-test both directions. Mind the layers: the service re-imports this module at every spawn (a file fix is live for new jobs at once) while the running bridge keeps the old list in memory until a restart — to fulfil a blocked-but-benign order meanwhile, re-dispatch its worker by hand (recipe: `references/content-gate.md`). **A phrase blocklist loses to rephrasing — add combination rules for categories that must never meet.** Requests arrived as 「没穿衣服的萝莉」 and then as a *complaint* (「你画的这个萝莉怎么有衣服」) that the dispatcher read as an edit order; enumerating phrases is a losing game, while one regex pair (minor-coded nouns × undress/remove-clothing verbs in the same message, either order) catches the whole family including the complaint-as-instruction trick. Keep the owner's line intact: ordinary 擦边 (比基尼/泳装/内衣/性感/湿身/兔女郎…) must pass — after every gate edit run a table test of ~15 allow-phrases next to the block-phrases, then restart the bridge.
- **Per-request processes must not each linger.** A job that stayed to watch its own 5-minute idle wait piled up **10** python processes under a burst; worse, a job that returned early (blocked, errored, no ComfyUI) left *no* watcher at all and the 4.5 GB stayed resident forever. Send the image, exit, and delegate idle-shutdown to one detached watcher (`image_service.py --watch <idle_s>`, singleton enforced by a heartbeat file, kills the 8189 listener once `last_use` is stale and no job lock is held). Verify it by running the watcher with a short idle and watching the port drop.
- **Let blocked requests rejoin the normal chat turn instead of answering directly.** When the gate or the game check fires, rewrite `content` with an instruction for the model ("…response in one or two spoken sentences, no lists, don't mention filters") and fall through — a hard-coded refusal string reads like a robot and cannot adapt to who asked.
- **ComfyUI pops a browser window on every start unless you say otherwise.** `comfy/cli_args.py` does `if args.windows_standalone_build: args.auto_launch = True`, and the standalone launcher always passes that flag — with an on-demand lifecycle (start per job, close when idle) that means one new browser window *per drawing*, which reads as "the bot keeps opening browsers". Confirm the correlation before believing it: compare the browser processes' `CreationDate` against the ComfyUI ready timestamps in the service log; they match to the second. Fix at the launcher (`--disable-auto-launch`; the disable check runs after the standalone one, so it wins) — the manual desktop path is unaffected because its .bat opens the browser itself. Re-check after any ComfyUI upgrade.
- **Relaxing a group rule means relaxing it in *both* gates.** `should_handle` (the cheap pre-filter) and `handle_event` (the real dispatch) each re-check "@ or wake word", and the inner one returns **silently**. Editing only the outer one gives: the `[in]` line appears in the log and then literally nothing else happens — no `[recv]`, no error. Put the decision in one shared helper and call it from both. Do not build per-feature bypasses of the mention requirement: the narrow "only image orders" window in this file was removed again at the owner's request after it caused uninvited renders — in groups every trigger (chat included) is @-or-name.
- **A broad verb+noun rule will match statements about the speaker's own actions.** 「我昨天画了张图」 contains verb→measure→noun and would queue a render; reject when 了/过/完 follows the verb. Every relaxation of the matcher needs a table-test line for the plain-chatter sentence it could newly swallow.
- **Detect on the user's words only — never on the text the bridge synthesised.** An image-only message gets a placeholder (「（对方发来图片，没有文字，请看图回应）」) and a reply gets `[被引用的消息] …` appended; both then flow into `text`, and a detector run on that matches its own scaffolding — a user who sent a bare photo got a generated picture back. Split the synthesised tail off before detection (drop everything from `\n[被引用的消息]`, drop the placeholder), and keep the detection input identical in the bridge and the service.
- **Match with three tiers, widest last, and reject meta-talk.** A verb+measure-word rule misses 「帮我生成色图」「帮我生成这个人穿泳装的照片」 because the noun sits behind other words — add a broad tier (画|绘制|生成 with an image noun inside ~12 characters) and a weak tier (来|跑|整|搞|做|捏 + measure word). What makes it safe is the *rejection* lists: a non-visual noun after the measure word (「生成一个想法」) and — the one that bit the owner himself — meta-talk after the image noun, because 「画图权限没有开放给每一个人」 matched verb+noun and got a nonsense render queued in a live group. Keep real misfires from the logs as table-test cases in both files.
- **Image orders from a *replied* image are a different feature: img2img.** A reply segment carries only a `message_id`, so resolve it with `get_msg`, pull the image out as a data URL and run the denoise workflow (`LoadImage` + `VAEEncode`) instead of `EmptySD3LatentImage` — **but since 2026-10-12 img2img defaults to the FLUX Kontext edit model** (`--engine auto` in `image_service.py`: base image → kontext, text-only → zimage; Kontext reads English instructions only, Chinese is auto-translated via DeepSeek). Z-image img2img is the fallback: denoise 0.5 (keep features) / 0.6 (outfit/transform), **never 0.75** (redraws everything, ignores the ask). Chain-edits only when the user says 「刚才那张/上一张」 (reads `cache/qq-images/last_out/<umo>.txt`); text that references 「这张/提供的照片」 with no attachment → ask for the image, don't hard-render. Cache the `get_msg` result — the same turn needs the replied image twice (once for the model's content, once for the dispatch) and without a cache you fetch and download it twice. Strip the pointing words out of the prompt («把这张改成戴墨镜的猫» → «戴墨镜的猫»): the model renders the *result phrase*, not the instruction.
- **Meta-talk sits on both sides of the trigger, so guard both.** Checking only what *follows* the match left 「…才能**触发这个画图**，还有以后我打游戏的时候…」 matching verb+noun, and the rest of the owner's sentence was used as the render prompt. Add a pre-check for the words just before the match (触发/这个/那个/才能/关于/提到…) as well as after it, and keep the owner's own complaints as test cases — the messages about the feature are the ones most likely to trigger it.
- **Game mode: react to the existing game probe instead of building a new one.** The Steam check that the game/voice gates already use (`_steam_now()` → the bot framework's watcher cache, Steam Web API fallback) is the same signal — a small daemon polling it every 30 s can stop the GPU/RAM-heavy self-started services and restore them afterwards. Rules that keep it safe: only touch services **we** started (never the user's browser, game, or system processes), remember which ones were actually running and restore exactly those, persist the state to a file so a daemon restart doesn't strand the machine in game mode, and debounce the exit (≈3 polls) because the Steam status blips to "not playing" during map loads and server switches. Keep the transitions **silent for the owner** — he asked not to be messaged on game start/end (『自己知道就好』), so leave `NOTIFY=False` in `game-mode.py`: services close and restore without a chat notice, and only an explicit future request should re-enable it. Keep the list of what to close in config/constants, not in the detection code.
- **A local model has no content moderation, so the blocklist has to grow from what actually arrives.** The first list missed 裸着 / 不穿衣服 — real users typed both within an hour — so re-read the group log after launch and add the terms people actually use, not the ones you'd write. Not every word users type belongs on it, though: the vague suggestive ones (色图 / 涩图 / 涩涩) are deliberately allowed — see the policy bullet above.
- **Check the persona before concluding the feature is broken.** Users reported "it won't draw for me" when the pipeline was fine: the phrasings simply weren't parsed, *and* when the request fell through to the model the chat instructions produced 「本鱼是只会打字不会画画的鱼」. Whenever a capability is added, state it in every instruction set that can answer about it (owner / second owner / guest) and forbid the "I can't do that" phrasing — otherwise the assistant denies having the feature you just built — seen twice: 「我不会画画」，以及克隆嗓上线后「我没有嗓子/我不会说话」。

## Shared-file discipline (more than one session edits this script)
- The write is last-writer-wins and a full-file rewrite silently drops the other session's fresh fix. Re-read the file before patching, change only the lines you mean to change, and grep for your own markers after any other writer or a restart.
- Restarting the bridge aborts in-flight turns (their replies are lost): sample a busy chat's message count twice ~10 s apart before restarting. The server-side turn survives, so the answer is still recoverable from the session.
- Make the contract explicit instead of trusting goodwill: put the script directory under git, take an advisory per-file lease before editing (`agentlock.py acquire <path> --owner <name> --reason "..." --ttl 900`, plus `release` / `status` / `prune` — `release` takes the **lock id** (printed by acquire/status), not the reason string; a conflicting acquire exits 1 and prints holder + reason + expiry), commit every change with a message, and append one line (`time | who | file | what | impact`) to a rolling `PROGRESS.md`.
- **Never coordinate through a chat-bound session.** POSTing a note into a session that a bridge or gateway serves can surface in the real chat; put requests in an `INBOX.md`-style file and answers in `PROGRESS.md`, and state the rule in shared memory so every session of the profile loads it regardless of cwd. To check whether something already leaked, pull `get_group_msg_history {group_id, count}` for the chat and grep the text.
- **Wake/policy flags are shared mutable state between sessions — put the owner's standing rule where both sessions read it.** A no-@ window added by the other session at the owner's request became *this* session's bug report the next day, and telling who set what took a git-log dig. Whenever the owner states a trigger/wake policy, change the flag and write the rule into the tracked `INBOX.md` in the same turn; before debugging "why does it answer uninvited", re-read the live `qq_bridge.json` (and the sibling session's recent commits) instead of trusting what you set earlier.

## Owner activity questions

- 用户要求：群友问「主人/贾梦在干嘛」时，机器人应拿到当轮实况，再用大肥鱼自己的人格口吻自然回答；不要直接发送机械面板。显式「视奸」指令仍可由原插件展示面板。
- 自然问法识别需覆盖「干嘛/干吗/干麻」等实际输入。将最新实况作为本轮上下文送入正常聊天路径，保留原有语音规则；不要用固定话术代替人格回答。
- 回答只依据实际取得的状态。应用名不等于屏幕内容，不能从浏览器进程推断正在浏览什么；缺少活动时长就不能说「摸了半天鱼」。数据离线、陈旧或获取失败时明确不知道，不沿用旧回合当作当前事实。
- 提示词写「直接回答、别查工具」不等于已经提速。必须测量真实收消息→模型完成→语音合成→发送各阶段耗时；词汇单测与健康接口通过不能证明群聊端到端回复成功。
- 识别要防误伤：「…干嘛用的 / 干嘛的」这类问用途的句子要排除、加长度上限；把已出现过和已排除的句子都留作表测用例。

## Persona / voice
- The outward persona is not in the bridge: it lives in `$HERMES_HOME/SOUL.md` (default profile) **and** in the same file for every guest profile the bot speaks through (`profiles/<guest>/SOUL.md`) — a persona written only to the default profile never reaches guests.
- **Human-sounding persona is a typing behaviour, not a traits list.** Traits ("聪明但懒/傲娇嘴甜") still yield tidy, complete, spec-style answers; what reads as human is cadence and imperfection: one short line at a time, spoken particles, few full stops, no headings/lists/summaries, react to the mood before the content, occasionally digress or admit not knowing, stay quiet in groups when there is nothing worth saying. Write those rules **plus two or three ✗/✓ micro-examples** into `SOUL.md` and the three instruction tiers, and remember existing sessions replay their old instruction text until their session entries are cleared. Full ruleset, examples and apply/verify checklist: `references/persona-voice.md`.
- `SOUL.md` is read when a session's system prompt is built, and a **live** session keeps that prompt cached inside its running agent (`state.db.sessions.system_prompt` is NULL on this install, so the cache is in memory, not in the row). Editing `SOUL.md` therefore reaches only sessions created afterwards — verify the file itself with a throwaway api_server session per profile.
- To move *existing* sessions onto the new persona, pick one of two paths (recipes in `references/bridge-operations.md`, tool `scripts/soul-refresh.py`): **inject** the persona text into the old session as a message (immediate — but a restricted guest profile often refuses it as a chat-channel message pretending to be system, which is correct behaviour, not a bug), or **restart the gateway** so every session rebuilds from `SOUL.md` on its next turn (definitive).
- Report which sessions still carry the old voice instead of claiming the persona is live everywhere; a live in-memory prompt does not follow the file.
- **Give each channel its own voice with the api_server `instructions` field, not by editing `SOUL.md`.**`POST /api/sessions/<id>/chat` accepts an optional `instructions` string: the server applies it as session-level guidance, remembers it for later turns on that session, and it does **not** show up in the visible chat history the way prefixing every message does. Use it for per-channel behaviour. The user's standing split is **WeChat = task channel, QQ = chat only**, so the bridge sends instructions telling the model to sound like a real person: one or two short sentences, spoken register, no headings or numbered lists, never "我在处理/已完成/任务进度" status reporting, knowledge questions answered in three or four witty sentences instead of a lecture, and requests to do work answered with「这种事去微信找主人」followed by a return to small talk. Keep that text in the bridge config so the user can tune it without a code change.
- **Capability tiers are per *sender*, not per chat, and instruction text is remembered per session.** Selecting by profile alone breaks the moment the user wants a second privileged person: route on the sender id (owner → may dispatch work; a secondary "master" → addressed warmly but restricted to chat/search; everyone else → chat only) and keep every tier's text in config. Changing that text does **not** rewrite sessions that already exist — the earlier guidance is replayed from the session — so delete the affected entries from `qq_bridge_sessions.json` and restart before believing the new rule; otherwise the privileged user keeps getting told to go elsewhere and reports "它没按指令做事".
- **Identity questions have one standing answer: 「是本鱼主人（QQ 1568468）弄的」.** Asked 「你是谁做的 / 你的本事谁弄的」, the bot says its master (QQ 1568468) made it — phrased fresh each time, never boilerplate. Write it in **two** places: `SOUL.md` (reaches new sessions) and every instruction tier in the bridge (chat / owner / second owner), because live sessions replay what they already remember. Before editing the tiers, check whether `qq_bridge.json` carries its own copy of a `qq_*_instructions` key (a JSON copy silently wins over the code default); after restart, verify all three senders' effective text with `instructions_for(uin, profile)`.
- **Reply in short paragraphs, sent as separate messages.** The user's standing complaint is that one long wall of text reads as AI ("要分段说，一长段一看就是AI"). Split on paragraph boundaries, keep each chunk to a sentence or two, send in order with a small gap, and serialize the sends so chunks from two chats cannot interleave.
- **New friends: send one shortest-possible greeting, and never accept the request yourself.** The owner approves friend requests by hand; the bridge only reacts to `notice` / `notice_type: friend_add` by sending one private message such as 「你好呀」 (config `friend_greet_text`). No self-introduction, no capability list, no 「有什么可以帮您」 — that opening line is the clearest tell of a bot and the user will call it out. Log incoming `request` events (who, comment, flag) so the owner can approve them, but never auto-accept, and repeat the same rule inside the chat instructions so the first *message* from a new friend is equally short. Send that greeting as **voice**, not text (`friend_greet_voice`, default on): the user's ask is 「你可以发语音了，而不是发你好文字」— a typed 「你好呀」 from a stranger still reads as a bot, a one-line voice message reads as a person. Reuse `_make_voice` + `send_voice` with the text path as the fallback, skip the voice while the GPU is busy with a game, and pre-warm the greeting once at startup (call `_make_voice(greet)` before it is needed) so the first new friend does not pay the TTS cold start.

- **Group wake stays @-or-name for EVERYONE, the owner included; the owner's privilege is power, not wake.** An owner-wide no-@ bypass (`group_owner_always`) makes the bot answer every casual line he types in a group: it butts into human-to-human conversations with analyses nobody asked for, and he reports it as 「没人触发它，它突然冒了一句」. Default that flag **off**, require the wake word / @ in groups for all senders, and keep private chats ungated (that is where 「想随便说就私聊它」 lives). If the user later asks for no-@ commands again, treat it as an opt-in per-chat flag, not a global default — and expect to remove it again. The per-feature no-@ window for image orders (`image_group_no_mention`) was granted and then revoked the same way, with the added rule that an order must say *what* to draw (「画一张什么」) before anything renders. In groups, everything — chat, song orders, draw orders — goes through @-or-name; the feature gates only decide what an accepted message means. When one trigger type still fires uninvited, sweep **all** the flags together (`grep -n 'no_mention\|owner_always\|free_chat' qq_bridge.json`) rather than fixing the one you remember.
- **「它会主动聊天」= 先查 `group_free_chat`，不是模型自作主张。** 2026-10-20 有人给群里开了「自由接话」（`group_free_chat: true` + 概率 0.5 / 空档 12s / 冷却 90s / 每小时 12 条），群里没人叫它也插话，主人当 bug 报。处置：把 `group_free_chat` 改 false → 重启桥接 → 用模块内 `should_handle()` 表测（主人没@→False、路人没@→False、@→True、叫大肥鱼→True）。另一类「主动消息」是 AstrBot `steam_monitor` 的开局/结束播报（`status_notification: true` 会往群发「myself 开始玩 X 了」）——主人早说过不用报，顺手关掉并重启 AstrBot。

## 群小游戏：你画我猜（2026-10-21 上线）
- 代码在 `qq-bridge.py` 的 `_ig_*` 一组函数：`_IG` 内存态按群存（{umo,round,used,scores,word,aliases,answered}），词库 `cache/draw-guess/words.json`。
- 触发：群里说「你画我猜」（不用 @，`should_handle` 里对开局指令和进行中的群放行）；猜词全是短句（≤16 字），命中词/别名 +1 分；「下一题/画猜榜/结束画猜」是指令；每题 90s 超时自动揭晓，单局封顶 20 题，答对后 3s 自动下一题。
- 出题复用 `_start_image_gen(umo, prompt)`（ComfyUI 要 GPU；打游戏时会被拦）；游戏消息用 `_ig_say` → AstrBot API 单条直发（不走 `send_qq` 的分段/表情包）。
- 坑：游戏进行中该群所有短消息都会被当猜词吃掉（不回、不进聊天）——这是设计；想聊天先「结束画猜」。

## Voice replies (answering with the cloned voice instead of text)
- **Send voice as the OneBot `record` segment**, not by uploading anything: `send_group_msg` / `send_private_msg` with `[{"type":"record","data":{"file":"file:///C:/path/line.mp3"}}]`. NapCat transcodes mp3 → QQ's silk itself, so there is no manual conversion step.
- **A bare Windows path is parsed as a URL and the send fails** (`文件处理失败: 识别URL失败`) even though the file exists — pass the `file:///` form; reuse whatever `_file_uri()` helper the image path already uses. The action channel is the same reusable NapCat WS, so no new plumbing is needed.
- Keep the chat readable: synthesise as voice only replies under a configurable character cap (≈90 chars) and let longer answers go out as text; on synthesis *or* send failure fall back to the text path so a reply is never lost; cache the audio by a hash of `(reference, text)` so a repeated line is not re-synthesised and the TTS server's cold start is paid once. Log the synthesis+send time per line — a silent 60 s wait reads as the bot being broken.
- **Never voice-read code or links — filter each chunk in front of the voice branch.** A written-in-chat HTML answer (`<!DOCTYPE html>`, `<html …>`, …) was synthesised and read aloud chunk by chunk into the group. `_voice_unsafe_text` rejects chunks containing code/URL markers or with a very low CJK ratio, and those go out as text; keep that guard on the send path (not just a prompt instruction) so future send-logic edits cannot bypass it.
- **The cloned-voice server shares the card with the user's games, so slow voice is a latency report — not a reason to turn the voice off.** With a game running the same line went from 2–8 s to ~36 s and the answering turn stretched past 4 minutes, so the user reports 「QQ 不回消息了 / 你不回我」 while every `[recv]`/`[send]` line in the log is healthy: answer that from the timestamps and the per-line synthesis timing, never as a routing bug, and do not go hunting in the bridge.
- **Never silently downgrade the voice to text when the GPU is busy.** Probing `nvidia-smi --query-gpu=utilization.gpu,memory.used --format=csv,noheader,nounits` (≥60 % util or ≥3 GB used → "gaming") and sending text instead produced 「现在语音怎么消失了？」 within the hour and had to be reverted: the clone voice is the feature the user asked for, and a fast reply that quietly drops it is worse than a slow one that keeps it. A slow-but-present voice is the default; if a downgrade is ever wanted it is an **opt-in flag that defaults off** (`voice_skip_while_gaming`), named to the user, and one line to flip back. Keep the probe able to fail open (a missing `nvidia-smi` must never silence the voice), and use it only to *explain* a slow reply.
- **Synthesis can *fail*, not only slow down, when the card is full — retry once, then fall back to text.** With a game (or another service) holding the VRAM the wrapper exits non-zero (`CalledProcessError`) and the reply quietly drops to text; a short pause plus one retry clears the transient OOM/timeout cases and is cheap enough to always do.
- When voice gets flaky, list the GPU's *other* consumers before changing any bridge code: `nvidia-smi --query-compute-apps=pid,process_name,used_memory --format=csv,noheader`. On a small card (8 GB) a stray ComfyUI or other inference service is frequently the real thief, and closing it is what the user actually wants — offer that instead of re-tuning timeouts.
- The synthesis call must be the *same* wrapper the Hermes TTS command provider uses (see the `voice-cloning` skill), otherwise the chat voice and `text_to_speech` output drift apart.
- Ask before making voice unconditional in group chats: any member can then talk the bot out of it ("别发语音了") in ordinary conversation, and the choice the user made gets silently reversed. Private-chat-only, or "voice while the owner is present", is usually what the user actually wants.

## Outbound reply hygiene
- **Sanitize every reply in the one send helper: strip `data:…;base64,…` URLs and drop whole lines that are ≥120 chars of base64.** An image posted in a group is fed to the model as a data URL; when the model echoes that string back instead of talking about the picture, the bridge splits it as if it were prose and posts ~150 chunks of "乱码" into the group (the chat API rejects most with `400`, so the log also storms). The user reports garbage, not a stack trace — clean the text where every send passes: data URL → placeholder, base64-only line → drop, remainder → truncate.
- **Cap the chunks and abort on repeated failure.** Send at most ~6 chunks per reply and `break` out of the loop after 2–3 consecutive send failures. An uncapped split turns one bad string into an unbounded retry storm against the chat API.
- Mirror the same rule into the per-channel instructions ("绝不要把图片的 base64 / data: 开头长串复述出来") so the prompt and the sanitizer defend the same seam.

## Multi-instance (a second QQ account on the same machine)

One NapCat = one QQ account. A second account needs a second QQ client + a second NapCat + a second bridge instance:

1. **QQ copy**: copy the whole `C:\Program Files\Tencent\QQNT` to `Apps\QQ-client1\QQNT` and launch *that* `QQ.exe` with a per-copy profile dir (`--user-data-dir=C:\...\Apps\QQ-client1\data`). Two installs run side by side; **without** the flag both fall back to `%APPDATA%\Roaming\QQ` and knocking the running bot offline is the observed result. Verify the flag actually reached QQ by reading the copy's process CommandLine before anyone logs in, and confirm the live identity with `CheckLoginStatus` / `get_login_info` (the uin must be the copy's own account) instead of trusting which accounts the picker happens to list. Keep the original process untouched; if the bot drops, kill all `QQ.exe`, re-inject via `NapCat.vbs`, and quick-login again.
2. **NapCat copy**: copy `NapCat.Shell` to `Apps\NapCat-client1`, and **fix `loadNapCat.js`** — it hardcodes the source install's path (`file:///C:/.../NapCat.Shell/napcat.mjs`); point it at the copy's own `napcat.mjs` or the copy silently runs the ORIGINAL NapCat code (QR/cache/config all land in the old dir). Set its `config/webui.json` port (6100) and its `onebot11_<uin>.json` `websocketServers` port (3011).
3. **Launcher**: same env-var recipe as `_hermes_start.cmd`, with `QQPath` = the copied `QQ.exe`; serve it via a hidden VBS. Config applies when the account logs in — set the OneBot ports BEFORE the login scan so no restart is needed afterwards. Log the second account in by generating a QR from the **copy's** WebUI (`6100`, `GetQQLoginQrcode`), never by clicking the copy's saved-account picker (it can list accounts saved in the default store). A restart loses the quick-login list entry (the scan account is not remembered) and forces a re-scan. **`onebot11_<uin>.json` only exists after that account's first login** — NapCat creates it with `websocketServers: []`, reads it at startup only, and does not hot-reload; adding the WS server later therefore needs an instance restart, which drops the QQ session (quick login is usually not restored) and forces another scan. When the uin is known in advance (re-hosting an existing account), write `onebot11_<uin>.json` with the instance's WS port BEFORE the first launch. When the client brings a brand-new QQ number (uin unknown until they scan), say upfront that onboarding takes two scans: scan → read the uin from `config/napcat_<uin>.json` / `onebot11_<uin>.json` → write the WS config → restart → scan again.
4. **Bridge instance**: the code supports `QQ_BRIDGE_ID=<id>` — config `qq_bridge_<id>.json` and sessions `qq_bridge_sessions_<id>.json` (create the JSON with forward-slash Windows paths; `\\U…` in a heredoc makes invalid JSON escapes). Set `napcat_ws` to the instance's WS, `bot_uin` to its uin, `owner_qq: []` + `guest_profile: <profile>` so every sender routes to that profile, and `send_via_napcat: true` (+ empty `astrbot_base_url`) — text replies otherwise go through AstrBot, which is bound to the FIRST bot account. Health: `curl :8791/health` → `ws_connected: true, bot_uin: <uin>`.
5. **Verify the send path** with a self-send (`send_private_msg` to the bot's own uin → retcode 0). Sending to a non-friend answers `retcode 1200` — the target must add the bot as a friend first; that is QQ policy, not a bridge bug.
6. **Profile hygiene for a client: restrict EVERY platform the client can reach, not just api_server.** `hermes -p <p> config set platform_toolsets.<platform> '["web"]'` for `api_server` **and** `weixin` (and any other adapter that profile serves) — a platform key that is absent falls back to the full default toolset, so a clone's WeChat path keeps terminal/file/patch even after api_server is narrowed. Verified failure: the client's WeChat agent (full toolset + the owner's cloned skill library) read `scripts/qq-bridge.py`, patched a new feature into it, took the agentlock lease, and sent a message through the OWNER's NapCat (3001) into the owner's group. Then remove every cloned MCP server (`hermes -p <p> mcp remove …`) and delete the operational skills from the clone's skill tree (bridge / messaging-gateway / astrbot / github-notify) — they document the owner's ports and are what led the agent there. Sing/draw still work because the bridge dispatches those directly, not through agent tools.
6b. **Shared bridge code is writable by any profile with file tools — new feature defaults must be OFF.** A client's agent added a 「群聊自由接话」 feature to the shared `qq-bridge.py` with `"group_free_chat": True` in DEFAULTS and `CONFIG.get(..., True)` in the gate, so the owner's bot would have free-chatted in every group on the next restart. Keep risky features opt-in: default `False` in DEFAULTS *and* in every `.get(..., False)` fallback, and enable per instance in that instance's JSON (`qq_bridge_<id>.json`). When a foreign change lands in the shared file, review the diff (`git diff`), release the lease it took (`agentlock.py status` → `release <id>`), and commit the reviewed version rather than reverting blindly.
6c. **On one Windows account, toolset isolation is soft — say so.** With `terminal`/`file` enabled a client profile can still read the owner's `.env`, configs and scripts, so rules and defaults only stop accidents, not intent. Offer the real isolation (Docker/VM/separate Windows user) instead of claiming the client cannot reach the owner's stack.
7. **One control channel per profile, scoped by env.** Register the same small `qq_admin` MCP in every profile with `--env QQ_NAPcat_WS=ws://127.0.0.1:<that instance's port>`; its tools are only `status / list_groups / list_friends / send_group / send_private` and every scope comes from the environment — a client profile therefore cannot address anyone else's bot, because there is no URL/path parameter to change. Add a SOUL line (「只能操作自己的号」) and verify both sides: the owner's profile reports 1150111337, the client's reports its own uin or 「未连接」 (its own QQ logged out), never the owner's.
